產品需求規格書 (PRD)：LINE 定期收款對帳小幫手
1. 產品概述
本服務為一款建置於 LINE 官方帳號（LINE Official Account）內的輕量化應用程式。核心價值在於解決群組或特定團體間「每月固定收費與對帳」的痛點。平台本身不介入任何金流，僅作為「數位帳本與自動催繳鬧鐘」，引導付款人透過 LINE Pay（一卡通 Money）的個人轉帳機制，直接將款項匯給發起人。

2. 系統環境與架構
前端介面： LINE LIFF (LINE Front-end Framework)，在 LINE 聊天室內直接開啟網頁介面。

後端系統： 雲端伺服器（負責處理商業邏輯、排程設定與資料儲存）。

推播通知： LINE Messaging API。

金流機制： 無 API 串接。依賴發起人提供個人的「LINE Pay 轉帳連結」或「轉帳 QR Code」，由系統展示給付款人進行 P2P 轉帳。

3. 使用者角色定義
發起人 (Initiator)： 建立收費專案、設定金額與日期、發出邀請、核對帳款。

付款人 (Payer)： 接受邀請加入專案、接收推播提醒、執行轉帳、回報付款狀態。

4. 核心功能模組需求
4.1 收費專案建立與管理（發起人端）
建立專案： 發起人可透過 LIFF 介面設定專案名稱、每月應收金額、每月約定繳款日。

設定收款資訊： 發起人須於系統內貼上個人的「LINE Pay 收款連結」或上傳「LINE Pay 收款 QR Code 圖片」（系統需提供防呆教學，教導使用者如何去 LINE Pay 內複製該連結）。

產生邀請卡： 專案建立完成後，系統透過 LINE 分享功能，生成精美的 Flex Message 邀請卡，讓發起人發送到特定 LINE 群組或私訊給好友。

帳本管理看板： 發起人可查看每個專案的當月繳費進度（分為：未繳費、待確認、已繳費）。

4.2 成員加入與約定（付款人端）
加入專案： 付款人點擊群組中的邀請卡，進入 LIFF 網頁同意金額與條款，即完成綁定。系統將紀錄該名付款人的 LINE UID。

退出專案： 付款人可申請退出專案，退出後不再收到該專案的繳費提醒。

4.3 自動化提醒與繳費流程（系統端 + 付款人端）
繳費前三日提醒（排程任務）： 系統於每月繳款日的前三天（例如：每月 5 號繳費，則於每月 2 號上午 10:00）自動觸發 LINE Messaging API，發送「繳費提醒通知」給專案內未繳費的付款人。

一鍵跳轉付款： 提醒通知內包含「前往付款」按鈕。點擊後開啟 LIFF 繳費頁面，頁面中央顯示發起人的「LINE Pay 轉帳連結按鈕」。付款人點擊後，會自動喚醒手機的 LINE Pay 轉帳畫面（跳出系統，進入 LINE 內建 P2P 轉帳流程）。

逾期提醒（選配）： 若超過約定日仍未標記為已繳費，系統自動發送逾期通知。

4.4 對帳與回報機制（雙向確認）
付款人回報： 付款人於 LINE Pay 轉帳完成後，須回到系統介面點擊「我已轉帳完成」。系統狀態由「未繳費」變更為「待確認」，並發送 LINE 推播給發起人：「某某某已回報匯款，請確認」。

發起人確認： 發起人查看自己的 LINE Pay 錢包，確認收到款項後，於系統看板點擊「確認收款」。該筆帳款狀態變更為「已完成」，系統自動發送電子收據推播給付款人。

5. 操作流程 (User Flow)
[發起人] 開啟 LINE 機器人 ➔ 點選「建立收費」➔ 輸入金額 1,000 元、每月 10 號扣款 ➔ 貼上個人 LINE Pay 收款連結 ➔ 轉傳邀請卡到群組。

[付款人] 點擊邀請卡 ➔ 按下「同意加入約定」。

[系統] 每月 7 號（前三天）自動推播通知給付款人。

[付款人] 點開提醒 ➔ 按下「轉帳去」➔ 畫面跳轉至 LINE Pay 並帶入發起人帳號與 1,000 元金額 ➔ 輸入密碼完成轉帳 ➔ 回到系統按下「已付款」。

[發起人] 收到「待核對通知」➔ 確認自己 LINE Pay 餘額變多 ➔ 在系統按下「確認收款」。

[系統] 結案該月帳款。

6. 開發備註與注意事項 (Developer Notes)
法規聲明： LIFF 介面上應有免責聲明，強調本系統僅提供資訊記錄與媒合，實際資金移轉發生於使用者與第三方支付機構之間，本系統不承擔資金糾紛責任。

防呆設計： 因 LINE Pay P2P 連結是固定的，若付款人自行更改轉帳金額，系統無法得知。因此對帳功能必須依賴「發起人的人工點擊確認」，工程師在設計資料庫狀態時，務必確保「待確認 (Pending)」這個中繼狀態的存在。

資料庫設計重點： 需包含 Users (使用者表), Projects (收費專案表), Memberships (專案與人員的多對多關聯), Transactions (每月期數的交易狀態紀錄)。

7. 技術架構與開發細節規劃 (Technical Architecture & Details)
為確保系統具備實作可行性、擴展性及安全性，補充以下工程端開發細節：

7.1 技術選型 (Tech Stack)
前端 (Frontend)： 使用 React (Next.js 或 Vite) 搭配 Tailwind CSS 進行開發。透過 LINE LIFF SDK (@line/liff) 取得使用者資訊 (Profile)。
後端 (Backend)： Node.js (Express/NestJS) 或 Python (FastAPI/Django)。提供 RESTful API 供前端呼叫，並負責串接 LINE Messaging API 執行推播與 Webhook 接收。
資料庫 (Database)： 關聯式資料庫 PostgreSQL，可搭配 ORM (如 Prisma, TypeORM)；或使用 Supabase 等具備 Auth 功能的 Backend-as-a-Service (BaaS) 方案。
排程系統 (Job Scheduler)： 採用 node-cron、BullMQ，或雲端原生排程 (AWS EventBridge / GCP Cloud Scheduler) 來定期檢查與觸發催繳邏輯。
基礎設施 (Infrastructure)： Vercel (前端) + Render/Zeabur (後端API) 進行無伺服器/容器化部署。

7.2 身分驗證與安全性 (Authentication & Security)
LIFF 登入驗證： 前端開啟 LIFF 時取得 idToken，並傳遞至後端進行 LINE 驗證。驗證無誤後，後端核發自家的 JWT (JSON Web Token) 作為後續 API 存取憑證，避免惡意竄改 LINE UID 進行越權操作。
權限管控： 所有寫入操作（如回報匯款、確認收款），API 皆須嚴格校驗 JWT 中的 user_id 是否與該專案的角色 (發起人/付款人) 相符。

7.3 資料庫結構設計詳細 (Database Schema)
Users (使用者表)： id (UUID), line_uid (Unique), display_name, avatar_url, created_at
Projects (收費專案表)： id (UUID), initiator_id (FK), name, amount (Decimal), pay_day (Int 1-31), payment_link, status, created_at
Memberships (專案成員表)： id, project_id (FK), user_id (FK), role (Payer), joined_at
Transactions (交易紀錄表)： id, project_id (FK), payer_id (FK), billing_month (YYYY-MM), amount, status (Enum: UNPAID 未繳, PENDING 待確認, COMPLETED 已繳, OVERDUE 逾期), notified_at (提醒時間), paid_at (匯款回報時間), confirmed_at (發起人確認時間)

7.4 排程與邊界條件處理 (Edge Cases Handling)
月底天數問題： 若約定每月 31 號繳費，遇到 28 或 30 天的月份，排程邏輯須自動校正，將繳款日與提醒日往前推算至當月最後一天。
時區處理： 系統內部時間統一以 UTC 儲存，推播提醒與前端顯示時需強制轉換為 Asia/Taipei (UTC+8)。
封鎖與解封鎖狀態： 實作 LINE Webhook 監聽 follow 與 unfollow 事件。若付款人封鎖官方帳號，系統應將其推播狀態設為停用，避免發送無效 Push Message 浪費 API 額度，並在介面標示提醒發起人。

7.5 API 介面規劃 (RESTful Endpoints)
POST /api/auth/login： 驗證 LIFF Token，核發 JWT。
POST /api/projects： 建立新專案。
POST /api/projects/:id/join： 付款人透過邀請連結綁定專案。
PATCH /api/transactions/:id/pay： 付款人點擊「我已轉帳完成」，狀態轉為 PENDING。
PATCH /api/transactions/:id/confirm： 發起人點擊「確認收款」，狀態轉為 COMPLETED。
POST /webhook/line： 接收 LINE 官方帳號的 webhook 事件。
