# AntiScam｜LINE OpenChat AI 防詐社群管理機器人 PRD

> 版本：v0.1（需求規劃）  
> 建立日期：2026-11-19  
> 專案：hub-google/LINE/AntiScam  
> 狀態：**PRD 已建立；尚未開發、串接或完成 LINE OpenChat 實機驗證**  
> 目標平台：LINE 社群（OpenChat），不是一般 LINE 群組或 LINE OA 聊天室。

## 1. 產品摘要

AntiScam 是以「偵測詐騙 → 快速保護社群 → 可稽核、可申訴」為核心的 LINE OpenChat 自動管理系統。

當有人（尤其是新成員）發布疑似詐騙、惡意導流、假冒管理員或大量廣告時，系統即時取得事件，透過明確規則、網址風險、行為特徵與 AI 分類，依社群設定採取警示、刪除違規訊息、移出成員與封鎖再加入等動作。管理員可從網頁後台監控多個社群與處理誤判。

**產品承諾必須以實機實測為準**：即時讀取 OpenChat 訊息、代管理員刪除他人訊息、踢人及封鎖，均不是現行公開 LINE Messaging API 為 OpenChat 提供的完整操作組合。PRD 所稱「自動刪除／踢出／封鎖」屬於需先通過技術驗證的目標，不能因商業工具宣稱支援就當作自建版本已取得權限。

### 1.1 核心價值

1. 優先阻止新加入帳號貼出投資詐騙、假客服、假中獎、虛假職缺、導流私訊及惡意網址。
2. 針對高可信違規案件，自動執行：**留下必要證據 → 刪除有害訊息 → 移出並封鎖違規者 → 發送簡短安全公告 → 紀錄處置結果**。
3. 對模糊案件採「先警示／先交人工」，避免 AI 錯殺正常討論。
4. 不必長期盯群；多社群統一在手機與電腦網頁後台查看。

### 1.2 目標使用者

- Owner：產品平台擁有者，管理連線健康度、帳號、全站安全與模組設定。
- 社群管理員：綁定社群、配置反詐規則、審查警報、救回誤判成員。
- 共同管理員：依授權審核事件、調整白名單與處置；不可超越主管理員權限。
- 一般社群成員：收到安全公告、可檢舉內容；不需註冊 AntiScam。

## 3. 範圍與成功標準

### 3.1 MVP 必須能完成的體驗（以 OpenChat 技術可行性為前置條件）

1. 管理員能新增社群、確認管理權限，看到「監控正常／權限不足／斷線／只讀模式」。
2. 新成員加入後進入「新成員觀察期」（預設 24 小時或前 3 則訊息，二者擇較長；可配置），非新成員仍接受基本偵測。
3. 收到文字訊息後進行字詞、網址、行為規則判斷；風險不足時才選擇性呼叫 AI。
4. 確認高風險的事件會根據該社群策略執行刪訊息、踢人、封鎖及警示；每個動作都追蹤實際成功／失敗。
5. 管理員可在後台查看「命中訊息 → 判定理由 → 規則／模型 → 處置結果」，對誤判進行人工解除或將使用者加入白名單。
6. 連線失效、權限不足、API 失敗時通知管理員，不得假回報「已刪除」或「已踢出」。

### 3.2 不在第一版範圍

- 一般 LINE 群組管理、LINE OA 客服、群組行銷廣播。
- 對全站 LINE 帳號封鎖（只能處理有權限的特定 OpenChat 社群）。
- 保證辨識真人身份、手機號、IP 位址，或跨社群精準識別同一自然人。
- 保證追回已被其他人讀取／截圖的訊息，或將 LINE 伺服器上所有歷史資料徹底刪除。
- 未實證可行前承諾 100% 自動刪除、100% 即時、所有媒體類型均可審核。

## 4. 主要使用流程

### F1：入群事件與風險觀察

- 取得新成員事件（若連接器支援）→ 建立社群內匿名 member key → 標記加入時間。
- 預設對新成員採加強審核；設定可調整為 1／6／24／72 小時、前 N 則訊息，或全時監控。
- 如只有訊息事件、沒有加入事件，系統只能使用「首次觀測時間」標記，不可宣稱是真實入群時間。
- 可配置對頭像／暱稱中常見詐騙字詞的偵測；改名不應直接等同詐騙。

### F2：訊息風險判斷

處理順序：
1. 資料正規化：繁簡、全半形、空白與零寬字元、Unicode 混淆處理。
2. 規則引擎：黑名單關鍵字、違禁短網址、網址導向、重複廣告模板、過度標記、相同內容洗版。
3. 上下文：是否新成員、是否短時間連續發送、是否多次違規；不可只因「投資」等一般詞彙就踢人。
4. AI 分類（必要時）：詐騙種類、風險分數、支持證據、模糊點；輸出可驗證的結構化資料。
5. 決策引擎：套用社群政策與白名單，產生單一處置計畫，避免並行重複踢人。

詐騙類別（可多選）：假投資／保證獲利、假中獎與領獎費用、冒充客服／管理員、虛假招募、釣魚連結／帳密蒐集、虛擬貨幣或博弈導流、要求私訊或加其他帳號、廣告洗版及其他。

圖片、QR Code 與圖片文字 OCR、附件、討論串、記事本可先列為下一階段；當連接器拿不到內容時明確顯示「未分析」，不可捏造 AI 檢測結果。

### F3：決策與自動處置

預設建議政策（數值為需求草案，正式上線須以標記樣本與實測校準）：

| 級別 | 觸發建議 | 預設行動 |
| --- | --- | --- |
| 緊急／明確惡意 | 已驗證惡意網址、重複釣魚模板，或多個獨立強訊號一致 | 先保存最少證據；自動刪除＋踢出＋黑名單＋警示（需管理員啟用「全自動」） |
| 高風險 | 明確詐騙引導但僅有單項訊號、AI 高分無可靠佐證 | 刪訊息＋通知管理員；由管理員決定踢出，或個別社群選擇放寬 |
| 中風險 | 疑似導流、語義不明或資料不足 | 私下管理員告警／人工審核；不自動踢人 |
| 低風險 | 正常討論／規則未命中 | 放行，不通知社群 |

- 每群模式：**僅監控（預設）／輔助管理／高信心全自動**。未經管理員明確啟用，不可開啟破壞性處置。
- 一個事件至多建立一個刪訊息任務、一個踢出任務及一個黑名單任務，採 idempotency key 去重。
- 管理員、共同管理員、機器人、群組白名單永不自動踢出；若疑似管理員被盜，只發最高級別私密警報。
- **「刪除訊息」與「收回自己發送的訊息」不是同一能力**：僅在連接器實際支援管理員移除他人訊息時才顯示「已刪除」；不可把本機隱藏當成所有成員已刪除。
- 推薦執行次序：記錄最少必要證據 → 刪除違規內容 → 踢出並封鎖 → 發一則不引用原詐騙網址的警示 → 更新稽核；任一步驟失敗，都單獨回報與嘗試有限、具退避的重試。
- 刪除失敗但踢出成功時仍須發警示及通知管理員手動刪除；不得將整個事件標示為完全成功。
- 需要人工確認的事件需可一鍵「刪除／刪除並踢黑／忽略／加白名單」，以避免多頁點擊。

### F4：社群公開警示訊息

例：

> 【AntiScam 防詐提醒】系統偵測到疑似詐騙或惡意導流內容，已依社群規則採取處置。請勿點擊陌生連結、匯款或提供驗證碼。如已操作，請立即聯繫官方客服與 165 反詐騙專線。

- 不直接公開成員帳號的個資、完整可點擊惡意 URL 或原始詐騙文案。
- 支援自訂公告樣板、是否 @ 使用者、群內通知開關、相似事件合併及冷卻時間（建議初始每群 60 秒）。
- 高密度攻擊時採彙總警告，不能每刪一則就洗版。
- 發送失敗回報管理員，不自行宣稱公告已送達。

### F5：私密管理後台（手機／電腦）

導航：**總覽／警報事件／社群設定／偵測規則／黑白名單／申訴與復原／系統狀態／管理權限**。

- 總覽：今日訊息監控量、警報數、刪文成功數、踢出成功數、待審、錯誤、連線狀態。
- 事件列表：時間、社群、暱稱或匿名識別、命中項目、風險等級、行動結果、處理人；依範圍篩選與搜尋。
- 事件詳情：必要的遮蔽證據、AI 解釋、觸發規則、動作流水紀錄與處置／申訴按鈕。
- 社群設定：逐群開關、觀察期、觸發門檻、公告樣板、權限能力測試、測試模式。
- 規則庫：新增／編輯／停用關鍵字、網域黑白名單、例外規則、版本回滾；可選擇先試跑分析歷史標記案例。
- 黑白名單：逐群有效，跨群同步必須明確啟用；支援解除、原因與有效期限。
- 管理員：Owner／Admin／Reviewer 唯讀或審核角色，所有高風險操作留 audit trail。
- UI 以繁體中文優先、適配 LINE 內建瀏覽器及一般瀏覽器。

### F6：人工檢舉與救濟

- 管理員可提交可疑訊息的文字／截圖／連結做人工分析；連接器無法讀取時仍能輔助判斷。
- 管理員可對案件標記「真陽性／誤判／無法判定」，做為規則改善與模型評估資料。
- 誤判處置：解除本系統黑名單、提示管理員重新邀請；**重新加入是否可自動操作，視 LINE 實際能力而定，不承諾一鍵恢復原有成員資格**。
- 白名單修改、強制踢出、批次刪除需二次確認或強權限，且有完整稽核記錄。

## 5. 技術架構及權限可行性

### 5.1 連接器設計（決定本案能否真正自動化）

抽象四類能力：

| Capability | 所需用途 | 開發前驗證 |
| --- | --- | --- |
| read_message / read_member_event | 讀取新訊息／入群事件 | 必須 |
| delete_other_message | 從 OpenChat 社群移除其他成員的訊息 | 必須 |
| remove_member / block_rejoin | 踢人、加入社群黑名單 | 必須 |
| send_group_notice | 在該社群發布提醒 | 必須 |

- **官方路徑**：LINE OpenChat 內建垃圾訊息過濾器、自動回覆、管理員手動移除；官方 Messaging API 主要針對 LINE OA 的聊天與一般群組，不能據此視為取得 OpenChat 管理員權限。
- **第三方／非官方路徑（技術研究）**：可參考 HAO 的產品範圍與開源專案的架構，但須獨立驗證可行性、帳號風險及 LINE 服務條款。不在 PRD 中假定可穩定登入、取得私有協定、繞過驗證或持續存活。
- 連接器每個能力須回報 supported / unsupported / degraded / unknown，附上測試時間與可讀錯誤；對使用者不可隱藏降級狀態。
- **Go/No-Go 門檻**：以專用測試帳號及測試社群，在真實 LINE OpenChat 成功讀取、刪除別人訊息、移除並封鎖測試成員、發公告，並確認手機端顯示一致，才啟動「全自動」開發；否則先交付以官方過濾器＋輔助判斷／人工處置為主的版本。

### 5.2 建議元件

- 前端：靜態管理後台，可先放 GitHub Pages 測試，正式環境再決定獨立網址；登入與權限控制不能只靠前端。
- 後端：長時間事件接收服務／Webhook 或持續連接器，負責取得事件與執行 OpenChat 管理動作。
- 偵測：規則引擎（先執行）＋可插拔 AI 分類服務（選擇性呼叫，提供逾時降級與成本上限配置）。
- DB：PostgreSQL（可用 Supabase；獨立 as_ 前綴及 RLS），保存規則、低必要度事件、處置與稽核；不要和 QueueMonster 的 qm_ 實體資料混合。
- 背景工作：可靠佇列／任務去重／重試與死信處理；不能把 GitHub Actions 定時排程當作秒級監控服務。
- 部署：以免費或低成本為優先，但須先量測執行環境是否有可靠持續連線；**免費不等於保證 24 小時在線**。

### 5.3 機密與資料保護

- LINE 帳號登入憑證、API Key、DB Service Role 必須放伺服器端 Secrets（如 GitHub Actions Secrets 或伺服器環境變數），**絕不寫進 Repo、前端 JS、localStorage、README 或日誌**。
- 預設不蒐集 IP、真實 LINE ID、電話或可跨社群辨識的身分資訊；若 LINE 不提供，不要推測。
- 原文證據最小化、URL 脫敏、限制瀏覽權限；初始建議 7 天刪除事件原文、30 天保留不含原文的處置摘要，管理稽核依必要期間保留。正式期限需再確認法務及成本。
- DB 使用每群／每管理員授權隔離、RLS、密鑰輪換；對管理員新增／移除、強制處置與規則異動留操作紀錄。
- 支援緊急總開關：一鍵停止自動踢人、自動刪文與公告，只保留偵測及管理員通知。

## 6. 資料模型（草案，不代表已建表）

全部使用 as_ 前綴，避免與 LINE Repo 其他產品資料衝突：

| Table | 用途 |
| --- | --- |
| as_communities | OpenChat 社群設定、模式、狀態、連線能力 |
| as_admin_memberships | 管理後台角色與群別權限 |
| as_connector_status | 連接器狀態、能力清單、最近驗證時間 |
| as_members | **群別內**匿名成員鍵、首次觀測／加入時間、觀察期狀態 |
| as_detection_rules | 規則種類、動作、版本、啟用與例外設定 |
| as_risk_events | 事件來源、訊息識別、類別、信心、匿名成員鍵 |
| as_moderation_actions | 刪除／踢出／封鎖／公告等任務與實際結果 |
| as_blocklist / as_allowlist | 社群黑白名單、原因、期限與操作人 |
| as_appeals | 誤判申訴、審核結果、復原狀態 |
| as_audit_logs | 管理員異動與安全事件 |

重要索引：(community_id, event_time)、(community_id, member_key)、(community_id, status)、(source_message_id)；以唯一索引與冪等鍵避免同一事件重複執行。

## 7. 事件處理與可靠性要求

事件流程：

1. Ingest：取得連接器事件並驗證來源與已授權社群。
2. Deduplicate：依來源訊息 ID／事件 ID 去重；同一使用者多則訊息仍分別檢查。
3. Analyze：規則優先、必要時 AI、套用群規與白名單。
4. Decide：生成單一 action plan、記錄評估依據。
5. Execute：刪文／踢黑／通知以獨立狀態機執行。
6. Confirm：取得 LINE 實際回應；必要時讀回驗證；未知結果不得當成功。
7. Notify：管理員事件推播、群內安全公告（受速率限制）。
8. Review：管理員覆核，誤判回饋規則並可撤銷封鎖。

異常策略：無權限 → 只讀＋私密警報；AI 逾時 → 規則引擎繼續、未知風險走人工；動作請求失敗 → 有限次重試＋指數退避；LINE 協定異動 → 連接器停用破壞性動作、標示降級。不能用無限重試造成洗版或封號。

## 8. 非功能需求與評估指標

以下均為**驗收目標，非已達成數據或 LINE 平台保證**：

| 項目 | 初始目標／測法 |
| --- | --- |
| 處置延遲 | 訊息可取得且連接器正常時，規則判斷 p95 ≤ 2 秒；整體刪除 p95 ≤ 5 秒，實機測量 |
| 事件不重複 | 同一訊息重送 10 次，不重複踢人或公告 |
| 降級安全 | 連接器斷線或權限不足時 100% 停止宣稱已執行的動作 |
| 誤判 | 以有標記測試集評估 precision／recall，確認門檻前不啟用自動踢黑 |
| 監控 | 連線存活率、事件積壓、刪除成功率、踢人成功率、人工覆核率、AI 成本 |
| 負載 | 單群瞬間 100 則／分鐘、多群併發進行測試，不漏稽核、不超額洗版 |
| 相容性 | LINE iOS／Android、桌面版與管理後台 LINE 內建瀏覽器／Chrome／Safari |
| 成本 | 先規則後 AI、可配置每日服務費上限，超額改人工而不是錯誤踢人 |

## 9. 頁面需求

### 9.1 總覽 Dashboard

頂部：社群選單＋監控狀態；中段：今日新增成員、風險事件、刪文成功、踢黑成功、待審；下方：最新五筆事件與七日趨勢。明顯顯示「全自動／僅監控」模式，不用假資料冒充正式統計。

### 9.2 社群設定

新增社群 → 能力測試 → 驗證管理權限 → 啟用偵測 → 選擇處置模式。提供醒目的破壞性動作啟用確認與緊急停止按鈕。

### 9.3 規則管理

分類 Tab：關鍵字、網址、洗版、新成員、AI 規則；新增、刪除、調整權重／嚴重度、試跑測試文字。可匯出與匯入 JSON，但每次修改有版本與操作人。

### 9.4 警報詳情

原文脫敏預覽、來源／時間／社群、判斷理由、各步驟結果、可手動重試與申訴記錄；所有高權限操作禁止未授權訪客直接操作。

## 10. MVP 開發階段與驗收 Gate

### Phase 0 — 技術可行性（第一優先）

- 確認官方 OpenChat 內建管理功能的實際設定與可用界線。
- 專用測試帳號加入測試 OpenChat，確認必要權限與操作是否能由合法、可維護的連接方式執行。
- 分別實測：即時讀訊息、讀新成員、刪除「他人」訊息、踢出、封鎖再加入、群內公告、權限撤銷與連線重建。
- 輸出證據表（實測時間、裝置、版本、操作成功與否、錯誤、風險）。**未通過 Gate 不宣稱可全自動，也不開始正式部署**。

### Phase 1 — 可用防詐 MVP

- 社群綁定、能力檢查、黑白名單、文字規則、管理頁面、事件／操作紀錄、人工覆核。
- 若 Gate 通過：有限度自動刪文＋踢黑＋群內警告；未通過：官方過濾器設定指南＋人工確認流程。
- 使用 20 組以上的正／反例測試，以及 2 個測試社群驗收。

### Phase 2 — AI 增強

- AI 文字分類、釣魚網址規則、同文洗版、可解釋原因與誤判回饋。
- 圖片 OCR、QR 辨識須視實際媒體取得能力另行驗證。
- 以真實標記樣本校準風險門檻；AI 單一結果不得直接造成不可逆處置。

### Phase 3 — 多社群與營運

- 多社群權限、跨群可選共享黑名單、健康監控、週報、規則版本與營運指標。
- 視需求增加入群審核、改名／刷圖、討論串／記事本支援。

## 11. 驗收案例（首批）

- AS-001：新成員發送已知惡意網址，觸發正確處置；逐項顯示刪文／踢出／封鎖結果。
- AS-002：正常談論股票投資與防詐新聞，不被直接踢人。
- AS-003：包含零寬字元、全半形、繁簡變體的同一違規文案可被規則正規化。
- AS-004：高可信詐騙重複送達 10 次只執行一次踢出。
- AS-005：管理員／白名單貼出可疑範例時，只發私密警報、不自動踢出。
- AS-006：LINE 權限被撤銷，系統改為降級且告警，不回報假成功。
- AS-007：刪除成功、踢出失敗時，管理員看見部分失敗與可重試按鈕。
- AS-008：AI 逾時／每日成本達上限，系統退回規則＋人工審核。
- AS-009：同群 1 分鐘內 20 則違規訊息，警示訊息合併，不洗版。
- AS-010：誤判解除黑名單後，記錄審核人、原因與時間；不宣稱自動復原入群。
- AS-011：未授權管理員無法查看其他群事件或使用破壞性操作。
- AS-012：在 LINE iOS／Android 實際確認刪除顯示與踢出結果，區分本機隱藏與全群刪除。

## 12. 待決策／不可偷渡的假設

1. **最大未知**：OpenChat 自動取得訊息與管理他人訊息／成員的穩定連接器是否存在，是否合法且符合 LINE 條款。
2. 是否允許使用非官方登入方式？須先評估封號、憑證與服務中斷風險，未確認前只做研究與模擬。
3. 自動踢黑應以多訊號高信心為預設，或允許各群自行選擇較嚴格的模式。
4. AI 供應商／模型、費用、證據保留期限與正式部署環境待實測決定。
5. 若無法取得真正的 OpenChat 訊息及管理能力，第一版以「**官方關鍵字過濾＋人工管理輔助**」替代，不宣稱已完成原本的全自動目標。

- 專案獨立放置於 LINE/AntiScam，與 QueueMonster、Workforce、group-cleanup 等程式和部署環境隔離。
