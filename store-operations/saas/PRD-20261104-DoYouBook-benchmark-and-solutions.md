## 2. 強制產品決策（覆蓋舊需求書的衝突規則）

### D-01 預約與叫號完全分離（P0）
- 舊需求書第 17 節「預約報到 → 自動建立 Queue Ticket」及 V2 Scope 的「Reservation -> Queue check-in」**在本 SaaS 產品不再適用**。
- 預約管理的「已報到／完成／未到／取消」只更新 Reservation，不應呼叫產號 RPC、建立 Ticket，也不在預約卡顯示「前往叫號管理」。
- 純預約店家完全沒有叫號入口；雙模組店家即使同一顧客也須明確由顧客另外取號，絕不背景轉單。
- 歷史上已關聯的預約與號碼不得直接清除；新行為改成完全分離，舊關聯仍可查稽核。各模組取消/刪除只影響自身；若舊資料有歷史連動需先做相容性分析，不能自動大批修改。
- 驗收：同一筆預約在「確認→已報到→完成」全流程中，Ticket 筆數不增加、叫號頁不出現該預約；同時取號的新 Ticket 不影響預約狀態。

### D-02 編號規則與手動重置（P0）
- 針對「預約管理」與「叫號管理」，**各自**有「編號前綴」設定與「重置編號」按鈕；由店家管理員操作，預設空白。
- 前綴允許空白，最多 3 個使用者可見字元（Unicode grapheme clusters）：中文、英文、數字、特殊符號均可；保留前後空白是否有效以規格化處理，預設去除外圍空白。前綴為純顯示，不得作權限/唯一鍵。
- 數字從 1 逐一增加，最多 9,999,999；不補零。顯示例：1、12、B1、診1、A-1；不可預設 A001 或 0000001。
- 重置後**新的**預約或叫號從 1 開始；舊紀錄編號及既有 LINE 訊息保持原樣，不准批次改號。預約與取號重置互不影響；多店／多分店互不影響。
- 內部唯一識別一律 UUID；另以 tenant + branch + module + numbering_epoch + sequence 做唯一性約束與交易鎖，避免並發同號。流水號建立、reset 與前綴快照需由後端處理，不能只在 localStorage 歸零。
- **同時存在舊批次有效號碼時的安全規則**：按重置先顯示「尚有 N 筆未結案」與新舊批次可能重號之警告。可保留舊批次待辦，但前後台需將批次識別清楚，任何同號歧義須顯示「舊批次」或以建立時間區分；不得誤叫、誤改或誤通知另一筆。工程實作前需確定已部署資料的相容方案與跨批次顯示方式，不能用刪舊資料換取重置。
- 驗收：不同模組各自從 1 開始，prefix 0～3 字元可設定；並發不重號；重置前已預約的編號不變；新批次的 1 與舊批次 1 不會選錯或發錯訊息。

### D-03 LINE-first 顧客身分（P0）
- 正常顧客流程：由 LIFF / LINE OAuth 授權後，自動帶 LINE 顯示名稱；不詢問帳密、姓名或測試入口；可直接預約/取號。
- LINE User ID 必須用驗證過的 ID token/官方取得資訊，不能信任前端回傳的 userId/name；同 Provider 可比對 ID，不同 Provider 不得把 userId 字串硬合併。
- 「不使用 LINE 的網頁預約」只列為另行開啟的 P2 兼容入口，**不是**預設顧客流程；若店家開啟，採最小必要聯絡資料及驗證碼／安全查詢，不得混淆 LINE 顧客的零輸入體驗。
- 已存在的 LINE 顧客紀錄跨裝置需依 verified identity 查詢，不能因匿名 Supabase session 換了就丟失。

### D-04 測試環境與資料不能被洗掉（P0）
- 保留現有 TEST-HQ／TEST-STAFF 一鍵測試入口與商家 QA 資料，確保每個瀏覽器能進入預期測試商家；禁止用假的 localStorage 預約或假推播替代真實 Supabase/LINE 驗收。
- 未經確認不得執行刪除正式商家、清空測試商家、覆蓋資料庫或重建 seed。測試資料與正式資料要在權限層隔離。
- 手機與電腦同一個響應式網址，不做「電腦版首頁」獨立產品；版本更新須自動偵測、避免要求顧客 Ctrl+F5。
- 過程中顧客只看到必要狀態（例如「資料更新中，請稍後」）；不顯示 Supabase、token、連線檢查等內部訊息。一般右下操作提示五秒關閉，重要錯誤不自動消失。

### D-05 刪除與取消不同（P0）
- 預約和叫號皆有可復原的「刪除」勾選；刪除是軟刪除，立即從顧客公開紀錄、進度及有效容量排除，**刪除/恢復均不發 LINE 通知**；店員後台留可稽核已刪清單。
- 「取消→改回已預約」屬狀態恢復，應**重新送出相同樣板**的預約成功 LINE 通知；不可另做格式不同的新通知。
- 新建與修改預約、取號事件都保存提交時間至秒，後台可檢視。任何事件通知需有 dedupe_key 防止重複。

## 4. 功能需求與完整解法

### P0 — 正確性、既有承諾及可用性（開發前必先複核）

**FR-001 預約與叫號分離**
- 解法：將預約「已報到」僅寫入 reservation 狀態；移除現有 staff check-in 自動產生/恢復 tickets 的後端耦合；顧客發起取號走完全獨立 RPC。
- UX：預約頁只顯示預約狀態、服務項目、時段、改期與取消；叫號頁只顯示票券、前方組數、現在叫號與控制。
- 驗收：既有預約報到不產生票券，任一頁修改不改另一頁，跨天未完成紀錄仍可查。

**FR-002 獨立前綴與手動編號重置**
- 解法：兩種 module 的設定欄、交易安全計數器與 epoch，保存每筆 display_prefix/display_number 快照；重置有二次確認和稽核。
- UX：「預約管理」「叫號管理」各一組編號前綴與「重置編號」；空白前綴時只顯示 1、2、3。
- 驗收：0～3 字元；不補零；兩模組及兩店互不干擾；跨午夜不意外重置已決定的批次。

**FR-003 LINE-first 身分／跨裝置**
- 解法：verified ID token → provider-scoped LINE identity → merchant customer mapping；必要時建立合併流程，但嚴禁用同名自動合併。
- UX：顧客不輸入姓名、密碼；失敗只給「重新授權 LINE」操作，避免無限登入迴圈。
- 驗收：同 LINE 帳號換手機/電腦能查原預約，未授權者不能查他人。

**FR-004 LINE 通知一致性**
- 解法：事件 outbox/任務表、事件唯一鍵、可追蹤狀態、後端重試；預約成立/恢復套用同一 Flex 樣板與資料來源，推播前重新查 DB 最新權限與狀態。
- UX：取號 LINE 訊息顯示號碼、建立時間、前方組數快照、【叫號進度】更新訊息與【查看即時叫號網頁】；不能宣稱 LINE 卡片會自己持續變動，按鈕觸發的是新查詢/新訊息。
- 驗收：建預約、恢復、改期、取消、取號、叫下一位、再叫與過號各有預期通知；刪除/恢復軟刪除不通知；同事件重試最多只成功送一次或具備可稽核的去重方案。

**FR-005 QA、權限、資料保留與版本更新**
- 解法：隔離 QA 專屬租戶、管理者權限、部署前 schema/資料備份與非破壞式 migration；前端版本檢查與靜態資產 cache busting。
- UX：TEST-HQ/TEST-STAFF 一鍵可測；同網址自適應，必要時重新整理提示自動處理；一般 toast 五秒關閉。
- 驗收：跨版本測試商家/預約/號碼仍存在；真實商家不出現在 QA 後台；沒有假狀態、資訊洩漏、過期頁。

**FR-006 軟刪除與恢復**
- 解法：deleted_at、deleted_by、reason、audit；API/Realtime/公開名額/通知皆排除已刪記錄；原記錄可恢復但不得同號重用原 uuid。
- 驗收：顧客即時不見、後台有刪除清單且可復原；不發 LINE；已發訊息無法撤回需 UI 說明。

### P1 — 與 DoYouBook 的直接競爭力

**FR-101 服務時間、工作人員與衝突防護**
- 每項服務設定時長（分鐘）、緩衝時間、價格、可用員工/資源、是否可併訂；套餐的時長依可組合規則計算，不以單一全店 slot_minutes 代替。
- 可用性算法：對每個資源檢查 [開始, 結束＋清場緩衝) 的時間區間是否重疊，開放時段/公休/名額約束同時判斷。
- DB 必須以交易及鎖或 exclusion constraint 保證併發不超賣。更改服務時長需重新驗證；若與下一筆衝突，顯示衝突詳情且不默默改其他預約。
- 驗收：60 分服務 10:00–11:00，相關人員 10:30 不可再被訂；不同獨立人員可並行。

**FR-102 營業時間與特殊日期**
- 支援週一到週日不同時段、午休、跨午夜、臨時休息、特定日開放、國定假日覆寫；不依賴全店單一 open/close。
- 由每店／每服務／每資源決定預約視窗、提前多久開放與截止、單筆最長時長。
- 驗收：公休日無新時段；既有預約在停業修改時先提示衝突，不自動取消。

**FR-103 顧客取消／改期限制**
- 店家可設「距離開始 N 小時內不得顧客自行取消/改期」，可分服務配置，預設清楚展示；不影響店員合權操作。
- 修改為原地修改，保留同一預約 UUID/編號及歷史變更；再次檢查容量、資源、截止與付款狀態，重新送對應通知。
- 驗收：時限邊界、跨日期與時區皆準確；已付款不允許不經退款/補差額程序偷偷改金額。

**FR-104 預約前自動提醒**
- 基於後端排程與事件 outbox，而非顧客持續開頁；支援店家開關及例如 24 小時／2 小時前（具備安靜時段），時間可調整。
- 更新/取消/刪除後舊提醒作廢，成功事件依版本去重；不能推播的顧客仍可在我的預約頁看到狀態。
- 驗收：取消後絕不收到舊提醒；跨時區與夏令時間的計算須正確；台灣預設 Asia/Taipei，系統使用 UTC 儲存並依店家時區顯示；免費額度不足時標記未送達，不偽稱已通知。

**FR-105 店員代客建立預約**
- 店員可輸入服務、時段、必要聯絡方式或選既有客戶，來源標記 STAFF/PHONE/WALK_IN；受 RBAC 與 audit 管理。
- 原則：LINE 顧客不必填姓名；非 LINE 客戶手動建檔以最小必要欄位處理，禁止僅憑電話碰撞自動合併不同人；付款或個資需另行驗證。
- 驗收：店員建檔占用同樣名額，不能靠代建繞過超額；若要管理員覆寫必須強制二次確認與留下紀錄。

**FR-106 商家開店精靈**
- 流程：1 基本資料/品牌 → 2 啟用預約/叫號 → 3 服務與時間 → 4 預約規則 → 5 LINE OA 使用模式 → 6 真實測試預約/取號/通知 → 7 複製專屬網址/QR/圖文選單。
- 使用總公司 OA 的店家不用有自己的 OA；已有 OA 者可選先借平台 OA，或走獨立綁定流程；未完成前明確標示不可用。
- 支援中途儲存、重跑不覆蓋設定、錯誤定位與進度提示；不要求顧客/店家手動複製 secrets 到公開前端。
- 驗收：新 QA 商家走完向導可在手機收測試通知；每步失敗可返回不丟資料。

**FR-107 PWA 與店員 Web Push**
- 做可安裝 PWA、店員手動同意 Web Push、後端訂閱裝置與撤銷權限；iOS 16.4+ 須從 Safari 加至主畫面才可使用網頁 App push，未支援時退回後台通知中心。
- 通知新預約、取消、改期等**店員事件**；顧客通知仍以 LINE 為主，不把員工推播混到客戶 OA。
- 驗收：同租戶只有授權職員收到；登出/撤權後不能再收到；拒絕推播仍能使用預約後台。

**FR-108 客戶簿與歷史**
- 每店維護 customer profile、LINE 經驗證身分、歷史預約、未到次數、偏好/備註（限制敏感資訊）、來源及最後互動。
- 營業員只看自身有權限店面，跨商家不能互查；原始個資查詢必須 RBAC/audit，允許資料匯出/刪除請求。
- 驗收：同一 LINE 顧客跨裝置檢索同店紀錄，其他店員不可取得未授權店的資料。

**FR-109 風控與黑名單**
- 店家可設定警示/限制模式、未到累積閾值、有效期限、理由與操作人；受阻擋的顧客要有申訴或店員人工覆核方式。
- 避免跨商家共用黑名單或靠姓名做拒絕；退款/預付狀態不可因封鎖遺失。
- 驗收：非黑名單正常預約；警示模式仍允許，但店員看到提示；封鎖僅影響設定店家。

**FR-110 店家品牌頁與公告**
- 店家封面/Logo/品牌色/簡介/地址/聯絡方式/服務價格/多張公告，預覽手機效果，提供 QR、IG/FB/LINE 分享。
- 上傳圖片要內容類型、大小、安全掃描/白名單、權限與儲存成本限制；未設定時提供簡潔預設，不需要遊戲化商店街。
- 驗收：手機/電腦同網址；品牌色不犧牲可讀性；未公開店家不可被搜尋到。

**FR-111 客戶資料 CSV 匯出**
- 依商家/分店授權匯出必要欄位；CSV escape、防 Excel formula injection、限制匯出筆數/稽核/下載連結有效期。
- 可匯出時間範圍與預約/取消/未到摘要，必要時去識別化；不包含 LINE token 或其他商家顧客資料。
- 驗收：中文字正確、下載可於 Excel 開啟、跨租戶無資料洩漏。

### P2 — 產業拓展與預約能力

**FR-201 四種可組合的預約模式**
- MODE_TIMED：依服務時長及資源排程（美甲、美髮）；MODE_SESSION：固定場次起訖與總名額（課程/活動）；MODE_CAPACITY：以時間區間占用量計算剩餘位數（教室/共享空間/寵物旅館）；MODE_DAY_CAP：每日最大服務/收容量（不限時至打烊）。
- 規則只在服務層挑選合適模式；同店可有不同模式，但每一預約只能採一套明確容量計算策略，不在前端混算。
- 支援每人上限、連續區間、數量票種、到打烊、重疊限制、臨時休假。
- 驗收：上午退場不佔下午名額；固定場次顯示完整起訖；每日名額滿只封該服務。

**FR-202 套餐／加購／多人票種**
- 服務可搭配加購與成人/兒童/寵物等明細，單價、數量、時間與資源用量由伺服器重算，存預約當下快照。
- 店員修改預約中的項目時，先模擬新增時間和容量影響，遇衝突可取消操作、不可「確認」就強制超賣；經授權覆寫要獨立開關與 audit。
- 驗收：加購改時間後價格/明細一致；已支付訂單不自動吞退款或重覆收款。

**FR-203 包場、封鎖時段與管理月曆**
- 可在週/月曆選日期與資源/時段建立 BLOCK/PRIVATE_EVENT，複選多時段，支持原因、可選費用及解除；可顯示各場剩餘名額。
- BLOCK 和預約走同一可用性引擎；已有預約存在時禁止無聲封鎖，必須先處理衝突預約。
- 驗收：封鎖後顧客無法新訂；解除後恢復剩餘名額而不動舊單；月曆數字與 DB 一致。

**FR-204 顧客自訂欄位**
- 每服務定義名稱、類型（文字/單選/複選/數字）、必填、長度、可見權限、保存期限；如「每隻寵物體重」可按預約數量重複。
- 嚴禁預設收集身分證、健康診斷、完整金融資訊；敏感情境需法務與資訊安全核准。欄位版本與答案保留快照，禁止 HTML 注入。
- 驗收：不同服務顯示不同問題；變更題目不破壞歷史預約。

**FR-205 Google Calendar / ICS**
- P2 首版只做資料庫 → Google Calendar **單向**同步與唯讀 ICS Feed；Google Calendar 的手動編輯不回寫本系統。
- 使用獨立日曆、OAuth 最小權限、事件外部 ID + extendedProperties、防重複及重試、更新/取消同步；斷線不影響預約成立，後台顯示同步失敗可重試。
- 驗收：同預約修改不會生出多筆日曆事件，無法同步時預約仍成立；撤銷連接後不再存取。

**FR-206 候補名單與空位遞補**
- 額滿可排候補，依時間/優先策略通知候補者；先給保留時限，過期才輪下一位，不可僅憑發出訊息就占用容量。
- 候補確認需重新由後端鎖定名額並防超賣；黑名單/通知未送達處理清楚。
- 驗收：多人搶最後一位只成功一筆；取消後僅依規則釋出。

**FR-207 兼容非 LINE 網頁預約（非預設）**
- 店家可選擇啟用；採手機驗證與一次性查詢連結／碼，最小化收集姓名電話，避免不驗證電話即讀他人紀錄。
- 不影響主要 LIFF 零輸入路徑，也不強制所有店家開放。
- 驗收：只登入 LINE 的使用者仍直接預約；訪客不能猜電話查他人的預約資料。

### P3 — 營運成長、收入與平台服務

**FR-301 營運分析**
- 指標：各服務預約數、預約→到店率、取消率、未到率、客戶回訪率、時段利用率、叫號完成率/等待分布、通知成功率、商家數與活躍店家。
- 資料源以 DB/事件紀錄為準，逐步做 SQL 彙總，不在每次載入全量前端掃資料；重要指標清楚寫分母/去重範圍。
- 驗收：跨天、軟刪除、測試店資料不污染正式營運報表；多店查詢授權正確。

**FR-302 線上訂金與金流**
- 只有商家符合代收/付款規範並完成合約、退款及稅務/對帳設計後才能上線；可比較 LINE Pay、信用卡、轉帳等通路，不能假定某支付可直接給平台個人或任意代收。
- 預約支付與商品 item-level paid/unpaid 走同一付款一致性設計，Webhook/查單確定後才更新已付款；退款與取消時限/訂金沒收需商家明確規則與必要告知。
- 驗收：付款回跳不是付款成功；重送 webhook 不重複入帳；付款失敗不產生已付標記。

**FR-303 動態定價／未來調價**
- 服務價可指定生效日期與優惠區間，價格由伺服器決定且在預約建立時留成交價、稅與折扣快照；與已付訂單的差額走額外補付/退款流程。
- 驗收：改新價格不回寫既有預約成交價；優惠過期後自動恢復正常價。

**FR-304 合法好友轉換分析**
- 僅在商家自有 OA 已完成授權且官方 API/權限允許時，記錄 follow/unfollow、同意與曾預約關聯；不能無授權批量讀好友名單。
- 只能用於合規行銷/服務，需退訂與權限控管；不同 Provider 的 LINE ID 不直接視為同一人。
- 驗收：顧客封鎖 OA 後不再顯示為可觸達；不向其他商家洩漏好友資料。

**FR-305 平台搜尋、曝光與營利**
- 總公司 OA 下提供公開店家依名稱、產業、地區與服務篩選；僅收錄商家主動 opt-in 公開資訊；同一顧客可跨店看自己的多店紀錄。
- 可設店家方案：免費入門、進階預約、進階叫號、跨店/分析等；方案差異應在功能與用量，避免針對 LINE 基本身分與資料可攜性做人為封鎖。
- 不急做遊戲化商店街；SEO 用獨立店家公開頁與結構化資料，但不可公開顧客記錄或臆造評價。
- 驗收：未公開店無法搜尋；同一顧客看到多店紀錄，但店家永遠只能看到自己的客戶。

**FR-306 通知成本與配額管理**
- 平台 OA／店家 OA 分別追蹤每月 LINE Messaging API 已使用數/預估剩餘/單位店家成本，讓店家開關非必要通知與設定緊急提醒優先順序；查額度以官方 API 為準。
- 同一商家在一個時間點只能選一個有效「通知發送者」供同一事件使用，不能總公司與店家 OA 重複發。
- 驗收：配額耗盡時不假稱成功送達，客戶網站資料仍正常，後台可見失敗原因。

## 5. LINE OA 多商家架構與流程（關鍵設計）

A. 無 LINE OA 店家：使用總公司 OA 的 LIFF／入口，商家識別從安全 merchant slug 取得，通知以平台 OA 發送；同一 LINE 用戶可跨店顯示本人紀錄，但店家資料隔離。
B. 有自家 OA 店家：經驗證的商家 Owner 在後台進行設定精靈；使用該商家 Provider 下 LINE Login/LIFF 與 Messaging API Channel；後端保存各 Channel 專用加密憑證與 sender mapping，webhook 必須先驗簽再路由租戶。不可把 Channel Secret 放 Git、公開 JS、URL、聊天內容。
C. 切換模式：需明確顯示哪些顧客需重新加入 OA 或授權，不能假設跨 Provider userId 可以沿用，也不能承諾總公司 OA 能推送到店家 OA 的好友。
D. LINE OA Manager 建立的 Rich Menu 與 API 建立的 Rich Menu 分屬不同管理面向；導入流程要明確提示替換／回復方法，避免覆蓋商家原有選單。
E. 連線狀態與通知送達分開：configReady / webhookVerified / customerLinked / friendReachable / messageAccepted / deliveredUnknown，每個狀態各自展示；API 接受送出不等於用戶已讀或收到。
F. 實時叫號：WebSocket/Realtime 讓**網頁**更新；LINE 訊息卡不承諾自動動態更新，採「查看即時叫號網頁」與「叫號進度」主動查詢/回傳最新快照，控制訊息配額。多商家不可依賴單一 OA 持續改一張訊息做全店即時更新。

## 6. 必要資料模型／API 方向（規格，不是本次 migration）

原則：沿用既有 public.so_ 表/RPC、Supabase Auth / RLS / SECURITY DEFINER，新增資料依租戶隔離；不得用新專案取代現有商家資料。工程實作前要先完成 migration 對照表與回滾策略。

建議擴充資料（名稱僅供實作者設計，勿直接執行）：
- so_tenants／branches 擴充：booking_enabled、queue_enabled、public_listing、timezone、notification_sender_mode、各店 branding。
- so_numbering_counters：tenant_id、branch_id、module(BOOKING/QUEUE)、epoch、next_value、prefix、updated_by；每筆 reservation/ticket 存 display_snapshot + epoch。
- so_services／so_menu_items 擴充：duration_minutes、buffer_minutes、capacity_mode、max_per_day、resource_id、required_staff_id、price_effective_range。
- so_resources／so_staff_availability／so_business_hour_exceptions：服務資源、班表、休假時段。
- so_reservation_items／so_reservation_events／so_time_blocks／so_sessions：加購明細、預約變更紀錄、包場、固定場次。
- so_customers／so_customer_identities／so_customer_flags／so_custom_fields：經驗證身分、備註、警示、服務欄位定義。
- so_notification_outbox／so_notification_attempts／so_webpush_subscriptions：事件發送、失敗重試、裝置撤權。
- so_channel_bindings：各商家 OA、Provider、驗簽來源、加密憑證引用（絕不暴露 secret）。
- so_external_calendar_events：預約 → GCal 事件 ID、同步狀態、最後版本；ICS feed token 要可撤銷。
- so_capacity_allocations／so_waitlist：不同模式占用時間區間與候補名額。
- so_audit 沿用：所有編號重置、權限、資料匯出、客服與重要狀態更動可追蹤。

API / RPC 規則：
1. 寫入預約、改期、取消、取號、重置、叫號、刪除皆由後端依 owner/tenant/branch/role 驗權限。
2. 同一預約的 status version / expected_state 做 optimistic concurrency；必要時 database transaction + row lock。
3. 回傳同一來源的「最新可用名額、票券號碼、紀錄版本」，前端不可自行預先假扣名額。
4. LINE 通知由資料庫事件/後端 queue 派送，不能以「前端成功 callback」作唯一可靠觸發。
5. 所有時間 UTC 存儲，顯示依店家時區；跨午夜預約/號碼不可無故自動刪除或結案；報表排除 QA 資料。
6. 符合個資最小化、保存期限、資料匯出與刪除、存取紀錄；新客製欄位特別審核個資與特殊敏感資訊。

## 7. 端到端 UX 與頁面架構

顧客（單一自適應網址）：
- 導流入口：總公司 OA 的「找店家／我的紀錄／商家合作」，或店家 OA 的 Rich Menu、QR、公開店家頁。
- 店家首頁：品牌、服務/時間、預約/取號兩個獨立入口（店家只啟一個則只顯示一個）。
- 預約步驟：選服務 → 選時間/人數/可選資源 → 確認資料與規則 → 完成；LINE 進入免填姓名。支援查詢/改期/取消。
- 叫號步驟：選（可選）服務 → 一鍵取號 → 顯示本號、現在叫號、預估等待與「時間 HH:MM 時前方還有 X 組」 → 按鈕查看網頁/刷新 LINE 進度。多店取號以店別卡片管理，禁止錯顯其他店資訊。
- 未登入/LINE 授權失敗：不展示未驗證的本人資料；單一明確重新授權操作。

店家（同一網站，手機/電腦自適應）：
- 工作台：今日預約、待處理叫號、通知狀態、必要統計。
- 預約管理：日曆/清單、狀態、加購/改期、店員代建、刪除/恢復、編號與重置；不出現「轉叫號」操作。
- 叫號管理：現在叫號、叫下一位、過號、再叫、服務中、完成、刪除/恢復、編號與重置。
- 菜單/服務：分類、名稱、價格、時長、容量規則、選擇條件；後續加資源與自訂欄位。
- 商家設定：時間/例外/品牌/公告/客戶簿/LINE/通知/PWA/匯出/付款/分析。
- 所有成功/失敗操作回饋包含具體業務結果；一般 toast 5 秒消失，重要錯誤需保持；同一套 LINE 通知樣板依事件不同填入資料，避免各頁再造一個版本。

## 13. 本次複核補上的完整方案（需納入開發與驗收）

**FR-112 預約送出前二次確認開關｜P1**
- 店家可在預約設定開關「送出前二次確認」，預設開啟。確認卡列服務、預約時間（含時區）、人數、主要價格或估價、店家條款及系統已驗證 LINE 暱稱；顧客按「確認預約」後才建立預約，按「返回修改」不建立。
- 二次確認不是提前占位；按最後確認時後端重新檢查可約容量／資源／最新價格，資料已變則提示重新選，不能誤顯示成功。
- 送出按鈕暫時禁止重複觸發，後端必須以 idempotency key 防重複預約；切換關閉確認卡仍需防重覆提交。
- **驗收 AC-112**：開啟時一定顯示一次確認卡，返回不新增；關閉時可直接送出；連按/網路重送不產生重複訂單；最後名額已被占用需失敗且不遺失選擇。

**FR-113 服務時長對顧客顯示可控｜P1**
- 每項服務有 show_duration_to_customer 布林值，預設開啟；若關閉，預約頁僅顯示「時間由店主安排」等合適說明，不公開敏感的內部估算分鐘數。
- 內部容量、相鄰時段檢查、清場緩衝與員工管理仍必須使用真實的 duration_minutes；這是展示層隱藏，不是將服務時長改為 0 或不檢查衝突。
- 未公開服務時長時，客戶端的付款摘要與外部公開分享頁亦不得洩漏內部分鐘數。到店時間及店員能否估出完成時間由業務規則定義，不能承諾客戶可使用該段時間。
- **驗收 AC-113**：隱藏的 90 分鐘服務，顧客看不到「90 分鐘」，但 10:30 仍不能占用其 10:00 起的同一資源；重新公開後不影響原預約。

**FR-114 到店／進行中／完成狀態，不得讓時間經過等於真實完成｜P1**
- 先區分「預約時段已結束」的**衍生顯示狀態**與「店員確認服務已完成」的**真實業務狀態**。不能單憑時間過了就把 NO_SHOW、CANCELLED、未到店者改成 COMPLETED，更不得連動叫號或付款。
- 店家可以選擇啟用自動完成，但須配置前置條件（例如確實 CHECKED_IN、已超過服務結束/緩衝時間、非取消/未到/刪除），在後端排程以版本檢查修改，留下 AUTO_COMPLETED/audit，商家可以更正並記錄原因。預設維持手動完成，避免誤判與客訴。
- 預約容量應依實際資源佔用區間計算，不靠 completed 狀態提前清空某筆已預留的時間。
- **驗收 AC-114**：過了時間但尚未報到不會被誤標已完成；已報到且店家開啟自動完成，達到設定條件才更新；任何自動完成不產生叫號票券、不更動已付款資料。

**FR-115 商家／分店／店員多角色管理｜P1**
- 差異化重點：即便 DoYouBook FAQ 表示目前主要單店主，我們產品原本已有 Owner/Manager/Staff 的 RBAC 與邀請框架，需補明跨店擴充與驗收。
- 同一商家可多位店員，Owner 依權限邀請/撤銷、指定可操作門市與預約／叫號模組；預設最小權限。離職/撤權立即失去後端資料讀寫權，並停用相對應的 Web Push 訂閱。
- 多分店的時段、資源、前綴/重置、OA 發信者、營運統計與顧客預約均須按 branch 隔離；平台管理者僅在合法授權範圍跨店檢視。
- **驗收 AC-115**：員工只操作獲授權的商家與分店；店員 A 不得重置無權門市編號；撤權後即使保留舊連結亦不能再改資料。首次建立/重邀請不會清空原店員設定。

**FR-117 手動電話預約與 LINE 身分安全合併｜P1**
- DoYouBook FAQ 宣稱可透過相同電話配對跨通路客戶；我們採用**經驗證電話持有人確認綁定**，不可僅使用相同手機號碼或相同姓名就自動合併客戶歷史。
- 既有 LINE Verified Identity 與經 OTP 驗證的電話號碼建立可稽核的 Identity Link；合併前提供簡明確認與爭議拆分流程，歷史預約保留原主鍵、來源與操作軌跡。
- 店員代建電話預約不需要顧客先登入 LINE；日後顧客加入 OA 可經明確授權找回紀錄。
- **驗收 AC-117**：不同人輸入同號但未驗證，無法取得他人歷史預約；成功驗證且同意後可看自己的舊電話預約；解除關聯不影響既有店家交易。

**FR-118 受控店員覆寫與通知偏好｜P1/P2**
- 前端容量不足/服務撞期時，預設禁止超收；若商家開啟「主管手動覆寫」能力，只允許指定角色、在詳列衝突與負載後二次確認，寫明覆寫原因並留 audit。禁止一般顧客或未授權店員使用，且不應允許造成不可實際履行的衝突。
- 店家可分事件類別設定「通知顧客／通知店員」以及關閉非必要事件；每個事件最多由指定平台 OA 或商家 OA 一方發送。對使用者個別抑制通知，應有合法的聯絡偏好／業務必要通知邊界，不能因行銷退訂就關閉應有的交易通知。
- **驗收 AC-118**：非授權店員無法繞過額滿；主管覆寫會顯示超額警示並留下可查理由；相同事件不會平台/店家 OA 雙重通知；通知偏好變更不刪掉既有預約。

**FR-119 預約工作台的日／週／月曆與即時確認｜P1**
- 日曆需突出「今天」、各日預約筆數及剩餘可用名額；切換日/週/月、依服務/員工/狀態/日期區間篩選，行動版可用卡片式日程替代難操作的橫向大型表格。
- 商家手動改期、現場新增、取消、包場時，日曆與列表來自同一 DB 可用性快照，不可讓已取消/已刪除的人繼續佔名額或顯示成有效預約；同時編輯須處理衝突版本。
- 客戶預約確認頁需展示清楚剩餘名額/服務時間是否公開/預估價格與取消規則；成功後顯示其確切預約編號與送出時間（秒）。
- **驗收 AC-119**：今日格醒目、同日容量一致；一筆在列表取消後日曆同步減少；10,000 筆資料仍可後端分頁；320px 手機可操作。

**FR-307 SaaS 商家訂閱與資料可攜｜P3**
- DoYouBook 公告的是免費及**未來可能 NT$299/月**，不是已實際收費。我們另做 SaaS tenant subscription 的方案、週期、發票/收據需求、試用、停用與欠費處理，不與顧客預約訂金/LINE Pay 交易資金混用。
- 店家無論升降方案或停用，至少保留合理的資料匯出/法定保存與刪除流程，並在開通時明確告知計費、LINE OA 訊息由誰支付及限制。付費狀態失聯不可讓顧客歷史資料無預警消失。
- **驗收 AC-307**：商家方案升降與停用不會轉移別家資料、扣款重試有冪等、可安全匯出自己的客戶及預約紀錄；顧客付款與商家 SaaS 訂閱分帳。

## 2026-11-05 實作增補：LINE 防濫用綁定、預約姓名／電話、候位恢復通知

## 2026-11-05 通用服務單位／多場次預約與獨立叫號（現行增補）

**最新產品決策：同一套網站、同一組預約／叫號功能，由店家勾選啟用多服務單位，不另開診所／醫院專版。** 本節覆蓋先前 D-01 對「任何連動均禁止」的限制；獨立模式仍為預設，其他原有需求保留。

### A. 開關與共用介面
- 原本 reservation/queue/calling 模組開關保留，另外由管理者設定三個可組合選項：
  1. multi_unit_enabled：啟用多服務單位。關閉時沿用單一預約／單一叫號介面。
  2. grouped_units_enabled：顯示服務分類（科別、櫃台類型、服務區等）。
  3. checkin_queue_enabled：預約報到後進入所屬場次叫號；要求啟用多單位、預約及叫號。
- 同一商家只有一個網站、一個商家身分與原有 OA 發送方式；醫師、診間、設計師、餐廳候位區、服務櫃台皆以「服務單位」表示。
- 服務單位沿用 so_booking_resources 加入分類與排序設定；場次以 so_service_sessions 儲存單位、日期、起迄時間與容量。同醫師不同診次為獨立場次。
- 顧客流程：商家首頁→選分類（若開啟）→選單位→日期→場次→預約或取號；LINE 身分驗證與通知共用既有架構。無多單位時不多一個操作步驟。
- 店員後台與企業設定仍是原網站；增加單位與場次管理、叫號場次切換及同店多隊列。
- 公開 board.html：單隊列沿用原大號碼版；多單位自動顯示多欄卡片，指定 session=UUID 可只看單一場次。禁止公開顧客姓名、聯絡資訊及 LINE 身分。

### B. 共用資料與交易規則
- 延用 so_reservations、so_tickets 各自 UUID、流水號、prefix 及重置；新增 service_unit_id、service_session_id，票券使用既有 reservation_id 連結。
- 場次預約 RPC so_unit_book_once 必須驗證 LINE 身分、名額和同請求去重；容量以未取消的預約人數計算，不能因同時送出而超賣。
- 報到 RPC so_unit_checkin 在同一交易內將預約改為已報到並建立一張關聯票券，重複點擊不再發新號；一般商家報到仍不自動產號。
- 現場抽號 so_unit_take_number 依指定場次處理，重複抽號只限制同場次。
- 叫號 RPC so_unit_call、so_unit_set_ticket_status 只在相同場次檢查服務中的票券；不同場次可同時叫號。
- 進度 so_unit_progress 依所屬場次計算；公開看板 so_unit_public_board 僅輸出號碼和等候數等無個資。
- 所有寫入的商家權限、LINE 身分、場次與容量均由資料庫驗證；不能靠前端，且不得清除既有商家/QA資料。
- 舊預約、叫號 RPC 不得因新增模式被改成全部自動連動；舊設定未勾選的店家行為必須相容。

- SQL 遷移：20261105_unified_service_queues.sql、20261105_unified_service_queues_records.sql；以前端 index.html 和 board.html 沿用既有 GitHub Pages 工作流程部署。

### D. 驗收情境
1. 一般單隊列商家不勾選任何新選項，原預約/取號/叫號及看板保持一致。
2. 一家商家有多分類、多單位、同單位不同時段，仍在同一網站完成全部操作。

4. 同一筆預約報到兩次只有一張票；不同單位可以同時叫號，不互相阻擋。
5. 公開看板顯示分隊列號碼但不顯示姓名、電話或 LINE ID；指定場次看板也必須正確。
6. 跨商家資料完全隔離，店員不能操作沒有權限的企業；手機與桌機版沿用相同網址。
