# 0. 文件使用方式

本文件不是概念提案，而是可直接交付開發 Agent 執行的「系統需求書」。

開發 Agent 應遵守以下原則：

- `MUST`：必要需求，不得省略。
- `SHOULD`：強烈建議，若未實作需在 PR / 開發紀錄中說明原因。
- `MAY`：可選功能，可依階段實作。
- 若需求文字與程式現況衝突，應以本文件最新版本為準，除非另有 ADR（Architecture Decision Record）覆蓋。
- 不得自行將「權限控制」、「付款一致性」、「叫號歷史」、「Audit Log」等需求簡化為純前端邏輯。
- 所有涉及身份、金流、權限、訂單、叫號狀態變更的寫入操作，MUST 由後端最終判斷。
- 所有資料模型需預留多商家、多分店能力，即使第一版只有單一測試店家。

# 1. 產品目標

建立一套以 LINE Official Account 為主要入口的門市服務系統，讓消費者與店家人員盡可能不離開 LINE 即可完成以下行為：

## 1.1 消費者

1. 預約日期與時段。
2. 選擇服務、餐點或商品。
3. 現場掃 QR Code 或從 LINE OA 取號。
4. 查看目前叫號、前方等待人數及預估等待時間。
5. 接收「即將輪到」、「已叫號」、「過號」等 LINE 通知。
6. 查看自己的預約、號碼牌、訂單。
7. 以 LINE Pay 支付全部或部分項目。
8. 到店後追加商品／服務並再次付款。
9. 查詢哪些項目已付款、哪些仍待付款。
10. 取消允許取消的預約或號碼牌。

## 1.2 店家／管理員

1. 查看當日預約。
2. 查看現場排隊名單。
3. 執行「下一號」。
4. 跳過／過號。
5. 重新叫號。
6. 指定某一號為下一位。
7. 將過號客插入下一位，但不破壞正常流水號。
8. 手動調整等待順序。
9. 查看顧客已購買的服務／商品／餐點。
10. 查看 item-level 已付款／未付款狀態。
11. 現場追加項目。
12. 建立補付款。
13. 標記現金／其他付款方式。
14. 管理員工角色與權限。
15. 調整營業時間、預約容量、排隊設定、服務與品項。
16. 查閱重要營運操作紀錄。

# 2. 非目標

第一版不以完整 POS、ERP 或會計系統為目標。

以下功能不屬於 MVP 必做：

- 完整電子發票系統。
- 會計總帳。
- 庫存成本會計。
- 薪資與排班。
- CRM 自動化行銷。
- 點數會員制度。
- 複雜優惠券引擎。
- 多幣別。
- 跨境付款。

但資料模型 SHOULD 避免讓未來擴充上述功能時必須整體重寫。

LINE OA MUST 被視為：

- 使用者入口。
- Rich Menu 容器。
- 通知管道。

LINE OA MUST NOT 被視為：

- 真正的授權系統。
- 真正的訂單資料庫。
- 真正的排隊狀態來源。
- 真正的付款狀態來源。

# 5. LINE 平台整合

## 5.1 LINE MINI App / LIFF

MUST：

- 使用 LIFF SDK 驗證使用者 LINE 身分。
- 前端取得的 LINE profile 資訊不得作為後端授權唯一依據。
- 後端 MUST 驗證 LINE 身分憑證／token。
- 不得相信前端自行提交的 `lineUserId`。

推薦：

```text
Client
  ↓ LIFF login
取得 token
  ↓ Authorization Header
Backend
  ↓ server-side validation
解析可信 line_user_id
  ↓
users / merchant_members
```

## 5.2 Rich Menu

一般使用者使用 Default Rich Menu。

Staff / Manager / Owner 使用 Per-user Rich Menu。

MUST 支援以下同步：

```text
merchant_members role 變更
        ↓
Rich Menu Sync
        ↓
LINE Messaging API
```

重要：

> Rich Menu 是 UI，不是 Permission。

即使使用者取得管理頁 URL，只要沒有後端角色權限，也 MUST 取得 `403 Forbidden`。

## 5.3 Rich Menu 建議

### Staff Menu



### Owner Menu

# 6. 多租戶模型

系統從 Day 1 MUST 支援 multi-tenant。

```text
Merchant
  └── Branch
       ├── Catalog
       ├── Staff
       ├── Reservation
       ├── Queue
       └── Order
```

## 6.1 Merchant

代表商家品牌／法人／帳號。

範例：

- XX 美髮
- YY 診所
- ZZ 牛肉麵

## 6.2 Branch

代表實體門市或服務地點。

每個 branch 可有不同：

- 地址。
- 營業時間。
- 預約規則。
- 叫號序列。
- 服務品項。
- LINE Pay 設定（若未來允許）。
- 人員。

所有營運資料 MUST 綁定 `merchant_id`，多數營運資料 SHOULD 同時綁定 `branch_id`。

## 7.1 角色

至少支援：

### CUSTOMER

一般消費者。

### STAFF

基本營運人員。

允許：

- 查看當日 queue。
- 執行叫號。
- 查看訂單必要資訊。
- 新增現場追加項目。

不允許：

- 新增管理員。
- 修改 Owner。
- 變更關鍵付款設定。
- 刪除 Audit Log。

### MANAGER

除 Staff 權限外，可：

- 修改 queue。
- 管理預約。
- 管理 catalog。
- 查看較完整營運資訊。
- 管理 Staff。
- 視政策執行退款。

### OWNER

最高店家角色。

可：

- 管理 Manager / Staff。
- 店家設定。
- 分店設定。
- 付款設定。
- 權限設定。
- 查看所有 Audit Log。

# 8. 管理員身份與邀請流程

## 8.1 原則

MUST 使用邀請制。

MUST NOT 提供：

- 「自己申請成管理員」。
- 只輸入某個 LINE Display Name 就成為管理員。
- 前端自行宣告 role。
- 以 Rich Menu 是否顯示判斷權限。

## 8.2 Invite Flow

Owner / Manager：

1. 開啟員工管理。
2. 點「新增員工」。
3. 選擇角色。
4. 產生 invitation。
5. 系統生成一次性 token。
6. 可呈現 QR Code 與連結。
7. 被邀請者用 LINE 開啟。
8. LIFF 完成身份驗證。
9. 顯示：

```text
XX 店邀請你加入
角色：Staff

[接受]
[拒絕]
```

10. 接受後建立 `merchant_member`。
11. invitation 標記 used。
12. 背景同步 per-user Rich Menu。

## 8.3 Invitation Token

MUST：

- cryptographically random。
- 不得可猜測。
- 一次性。
- 有 expiry。
- 綁 merchant。
- 綁 branch scope（若有）。
- 綁 role。
- 使用後不可重用。
- 被撤銷後不可使用。

資料：

```text
staff_invitations
- id
- merchant_id
- branch_id nullable
- role
- token_hash
- expires_at
- status
- invited_by_user_id
- accepted_by_user_id nullable
- accepted_at nullable
- created_at
```

Token MUST 只儲存 hash，不儲存明文。

```text
CHECKED_IN

CANCELLED_BY_CUSTOMER
CANCELLED_BY_MERCHANT
```


# 13. 關鍵規則：號碼與服務順序分離

這是系統核心要求，MUST 遵守。

錯誤設計：

```text
current_number = 50
```

然後若 25 回來：

```text
current_number = 25
```

這會破壞流水號、等待順序、統計及通知。

正確設計：

- Ticket Number：顧客永久號碼。
- Queue Ordering：實際候位順序。
- Serving Ticket：目前服務對象。

例如：

```text
Tickets:
25 PASSED
50 SERVING
51 WAITING
52 WAITING
53 WAITING
```

管理者選擇「25 下一位」：

```text
Service sequence:
50 -> 25 -> 51 -> 52 -> 53
```

Ticket number 不變。

# 14. Queue Ordering

推薦使用明確的 Queue Entry / sequence model。

```text
queue_positions
- id
- queue_id
- ticket_id
- sort_key
- inserted_reason
- inserted_by
- created_at
```

或者：

```text
queue_tickets.queue_rank
```

但若頻繁 reorder，SHOULD 使用 fractional ranking / LexoRank 類似策略，避免每次重排大量 rows。

MVP 亦可使用 integer sequence + transaction。

# 15. 叫號操作

Staff UI MUST 提供：

- 下一位。
- 再叫一次。
- 開始服務。
- 完成。
- 過號。
- 取消。
- 指定下一位。
- 插入下一位。
- 手動調整順序。

## 15.1 「下一位」

後端：

1. 驗證 staff 權限。
2. lock branch queue。
3. 找下一個 eligible WAITING / RETURNED ticket。
4. 標記 `CALLED`。
5. 記錄 called_at。
6. 建立 queue_event。
7. 發通知。
8. 回傳最新 queue snapshot。

MUST idempotent-safe，避免 double click 連跳兩號。

建議 client 傳：

```http
Idempotency-Key: UUID
```

## 15.2 過號

`CALLED -> PASSED`

MUST 保存：

- 過號時間。
- 操作者。
- 原順位。
- event。

## 15.3 過號回來

`PASSED -> RETURNED`

預設不可自行破壞正常 queue。

店家設定：

```text
return_policy:
- APPEND_END
- INSERT_AFTER_N
- STAFF_DECIDES
```

MVP 建議：

`STAFF_DECIDES`

管理員可：

```text
[排到最後]
[下一位]
[插入第 N 位]
```

## 15.4 指定 25 號先服務

假設：

```text
Serving = 50
Waiting = 51,52,53
Passed = 25
```

操作：

```text
POST /queues/:id/tickets/:ticketId/insert-next
```

結果：

```text
Current = 50
Next = 25
Then = 51,52,53
```

50 完成後叫 25。

25 完成後 MUST 回到 51。

# 17. 預約與 Queue 合流

系統 MUST 支援 Reservation customer 到店後進 Queue。

Flow：

```text

        ↓
Customer arrives
        ↓
CHECKED_IN
        ↓
Create Queue Ticket
        ↓
Queue
        ↓
Serving
        ↓
Reservation COMPLETED
```

避免同一預約重複 check-in：

```text
UNIQUE reservation_id on active queue ticket
```

或以 transaction 保護。

# 22. LINE Pay

正式串接使用 LINE Pay Online API v4。

核心流程：

```text
Order / selected unpaid items
       ↓
Create internal Payment
       ↓
POST /v4/payments/request
       ↓
取得 transactionId + payment URL
       ↓
Customer LINE Pay auth
       ↓
Redirect confirmUrl
       ↓
Server verify internal payment
       ↓
POST /v4/payments/{transactionId}/confirm
       ↓
Successful
       ↓
Payment = PAID
PaymentAllocation applied
Order totals recalculated
```

## 22.1 Payment Request

後端 MUST 產生自己的：

- internal orderId。
- payment record。
- idempotency key。
- expected amount。
- expected currency。

不得由前端直接指定可信金額。

## 22.2 Confirm

Confirm MUST 比對：

- transactionId。
- orderId。
- amount。
- currency。
- internal payment status。

不可只因 redirect 回來就標記付款成功。

## 22.3 Payment Idempotency

MUST 防止：

- 使用者 double tap。
- confirm URL refresh。
- retry。
- callback 重複。
- network timeout 後再次送出。

同一付款最多只能成功 allocate 一次。

建議：

```text
UNIQUE(provider, external_transaction_id)
UNIQUE(idempotency_key)
```

## 22.4 Payment State

```text
CREATED
REQUESTED
AUTHORIZED
PAID
FAILED
CANCELLED
REFUND_PENDING
PARTIALLY_REFUNDED
REFUNDED
```

實際 LINE Pay confirm/capture 模式依商家申請與整合方式定義。

# 42. Security Requirements

本章全部為 MUST，除非另註明。

## 42.1 Authentication

- 所有管理 API MUST authentication。
- 所有付款 API MUST authentication。
- 不接受 client-provided user identity。

## 42.2 Authorization

每個管理寫入 API MUST：

```text
authenticated user
        ↓
merchant_members
        ↓
status active
        ↓
branch scope
        ↓
permission
```

## 42.3 IDOR 防護

例如：

```http
GET /staff/orders/123
```

即使 user 是 A 店 Staff，如果 order 123 屬於 B 店，MUST `403` 或 `404`。

任何：

- orderId。
- ticketId。
- reservationId。
- paymentId。
- branchId。

都必須檢查 tenant ownership。

## 42.4 CSRF

若使用 cookie session，MUST 實作 CSRF protection 或 SameSite + token strategy。

若使用 Authorization bearer token，需避免 token 被注入或外洩。

## 42.5 XSS

User note / item name / merchant-defined content MUST escape。

若支援 HTML，MUST sanitize。

## 42.6 SQL Injection

MUST parameterized query / ORM。

## 42.7 Rate Limit

至少：

- auth。
- invitation accept。
- ticket create。
- payment request。
- admin mutation。

## 42.8 Secret

不得 commit：

- LINE Channel Secret。
- Channel Access Token。
- LINE Pay Channel Secret。
- DB password。

使用 secret manager / env。

## 42.9 Logs

不得記錄完整：

- Access Token。
- LINE Pay secret。
- session token。
- invitation plaintext token。

## 42.10 HTTPS

Production MUST 強制 HTTPS。

# 44. Concurrency

這個系統很容易遇到多店員同時操作。

MUST 處理：

## Case A

兩個 Staff 同時按「下一位」。

預期：

- 不得同時叫兩個不同號。
- 不得把同一 ticket 重複 call。

解法：

- DB transaction。
- queue-level lock。
- Redis lock（多 instance）。
- idempotency key。

## Case B

最後一個預約 slot 同時被兩人選。

預期：

只有一人成功。

## Case C

兩個付款請求同時支付相同 item。

預期：

不可 double pay。

Payment allocation creation MUST transaction-lock selected unpaid items。

# 96. 最重要的 Domain Invariants

以下永遠必須成立：

### Invariant 1

每張 Queue Ticket 的 `ticket_number` 建立後不可因 reorder 改變。

### Invariant 2

實際服務順序與 ticket number 分離。

### Invariant 3

同一 Order Item 不可被成功支付超過其應付金額。

### Invariant 4

Order `paid_total` 必須等於有效 payment allocation 合計。

### Invariant 5

任何 Staff operation 都必須通過 backend RBAC。

### Invariant 6

任何 tenant resource 都必須驗 merchant / branch ownership。

### Invariant 7

第三方 redirect 不等於付款成功。

### Invariant 8

任何敏感手動變更可追溯到 actor。

### Invariant 9

同一 invitation token 最多成功 accept 一次。

### Invariant 10

同一 queue 的 `call-next` 在 concurrency 下不得跳號或重複 call。

# 99. 最終產品原則

這套系統不是「聊天機器人」。

它是一套：

> 以 LINE OA 作入口、以 LIFF / LINE MINI App 作 UI、以後端作唯一可信狀態來源的門市營運系統。

核心產品模型為：

```text
LINE Identity
   ↓
Merchant / Branch
   ↓
Reservation / Queue
   ↓
Order Items
   ↓
Payments
   ↓
Fulfillment
```

管理員 UI 與一般客人 UI 可以不同，但：

> UI 差異只改善體驗，真正的安全性永遠來自後端 Authentication + Tenant Isolation + RBAC + Audit。

Queue 的核心原則：

> 「號碼」是顧客識別；「順序」是營運狀態。兩者不得混為一談。

Payment 的核心原則：

> 「一張訂單是否已付款」只是計算結果；真正付款狀態必須落在 Payment + Allocation + Item 層。

只要以上三個原則不被破壞，後續才能安全擴充到預約、美髮、美甲、診所、餐飲、寵物美容、維修、洗車等不同場景。
