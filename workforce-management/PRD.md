## 0.A 2026-11-06 多企業組織與帳號架構（已實作）

1. **一企業一 Tenant**：`wm_tenants` 及既有 `wm_branches`、`wm_departments`；真實企業由註冊且驗證電子郵件的 Owner 建立。第一名員工資料透過安全 Trigger 與 Owner UUID 關聯。一個 Auth UUID 可在不同 Tenant 擁有不同角色。
2. **企業擁有者**：`role=owner`，全公司資料範圍。可建立部門、管理角色、發送員工單次邀請。企業 Owner 角色不可由普通成員編輯 RPC 任意新增或解除。
3. **人資管理者**：`role=hr`，全公司人員可見且可處理人資事項；不可藉由普通角色編輯介面變更公司 Owner／HR 角色。
4. **主管與組長**：`role=manager`，由 `wm_members.reports_to` 決定管理關係，不以固定單層店長判定。職稱放 `wm_members.job_title`；組長與經理使用同一 Manager 權限類型但具有不同上級／下級。主管看得到本人與管理鏈以下員工、只能審核下屬，不能審核自己或平行部門員工。
5. **一般員工**：`role=employee`，只可看自己 RLS 授權的資料，沒有角色編輯／審核權限。請假、加班、補卡維持各自獨立按鈕。
6. **員工啟用**：Owner／HR 在「組織與權限」輸入員工 Email、姓名、角色、職稱、分店、部門、直屬主管；伺服器新增未綁定的 `wm_members` 與 `wm_org_invites`，產生 48 位 hex 單次 Token。Token SHA-256 儲存於 DB，7 天有效；員工用指定 Email 註冊／登入及驗證後才可完成 Auth UUID 綁定。邀請只在有權限的企業管理員畫面顯示，需自行將連結傳給該員工；不假裝有自動寄出 Email。
7. **資料庫權限與稽核**：`wm_private.is_org_descendant` 判定管理鏈，`wm_private.member_visible` 保護跨企業／跨部門員工資料，`wm_private.can_approve_member` 與請假／加班狀態 Trigger 限制主管審核。禁止主管形成循環或跨企業指派；角色與上下級異動寫入 `wm_org_role_audit`。敏感薪資 `hourly_rate` 仍不可由一般員工 REST 查詢。
8. **共用 DEMO 與真正企業資料隔離**：共用 DEMO 供匿名預覽，正式測試帳號在獨立的兩家虛構企業，不能借 Demo 權限直接操作別人的公司。若使用者變更登入身分，舊的 Demo 載入會被丟棄。
9. **自動化驗收**：測試矩陣詳見 `ORG_HIERARCHY_TESTPLAN_20261106.md`；測試使用真實 Supabase Auth、Playwright UI、REST RLS 安全斷言，以及實際操作 PNG，不以單純資料庫種子充當通過證據。

## 1. 產品定位、目標與非目標

### 1.1 產品願景

企業透過平台建立公司與分店、邀請員工綁定 LINE；員工從 LINE OA 圖文選單開啟 LINE Web App／LIFF 或對話式入口，查班表、填可上班時段、打上下班卡、申請請假／換班／補卡／加班；主管在手機或電腦審核、排班、追蹤缺勤；人資匯出依法保存的出勤、假勤與工時報表。支援一個人同時受僱於多家使用本平台的企業。

### 1.2 目標使用者

| 角色 | 主要工作 |
|---|---|
| 平台管理員（Platform Admin） | 企業開通、方案與系統營運、異常處理；不得任意閱讀個別企業資料 |
| 企業擁有者／人資（Owner/HR） | 組織、員工、工作規則、假別、班表、報表、核銷與權限 |
| 分店／部門主管（Manager） | 排班、人力需求、審核假勤／換班、處理缺卡異常 |
| 員工（Employee） | 查班、填可上班時間、打卡、請假、換班、查看工時與假別 |
| 代班／臨時員工（Part-time） | 兼職工時、跨店排班、交換班別、提出時段偏好 |

### 1.3 成功指標（上線後追蹤）

- 已邀請員工的 LINE 帳號綁定成功率 ≥ 95%（需排除使用者自行中止授權）。
- 有班表員工每週查看班表的比率、員工按時打卡率、缺卡異常結案時間。
- 請假／補卡平均核准時間、排班工時節省量、跨店排班衝突數。
- 多租戶資料越權存取事故 **0**；已送達但重複打卡紀錄 **0**；原始出勤紀錄遺失 **0**。
- 上述門檻為產品目標，非既有實測數據。

### 1.4 非目標

不做完整人事招募 ATS、財務總帳、員工薪資發放或報稅服務。**薪資計算所需的工時／假勤資料匯出、薪資系統串接界面仍在範圍內**。若未來擴充完整薪資，須獨立 PRD。

## 2. 產品入口與 LINE 身分策略

### 2.1 入口模式

1. **平台總公司 LINE OA（預設，MUST）**：未自行經營 OA 的企業與員工，透過總公司 OA 入口使用平台，依已綁定企業選擇工作場域。
2. **企業自有 LINE OA（MUST）**：企業完成 Channel／Webhook 驗證後，可把相同 SaaS 功能入口放在自己的 OA Rich Menu；外部 OA 必須經明確授權與隔離管理。
3. **獨立網頁／桌機（MUST）**：不要求使用者先掃 QR code 才能進入；LINE Login／LIFF 完成驗證後回原工作頁。桌機不可假設具備手機自動登入。
4. **純 LINE 對話操作（SHOULD）**：打卡、查班、申請請假、待審提醒可由文字、按鈕或 Flex Message 操作；複雜填單一律可進 LIFF 網頁完成，不能只靠 AI 解讀。

### 2.2 身分與安全

- LINE Login 為身分驗證方式之一；**LINE 使用者 ID 不是授權角色**。伺服器驗證 ID Token、nonce、state、audience，建立自己的 Session。
- 以 `(LINE Provider / Channel, lineUserId)` 形成外部身分對應，勿假設不同 Provider 的 LINE 使用者 ID 永遠相同。
- 員工須接受企業邀請、完成必要身分確認，才能建立 `EmployeeMembership`；僅加好友或掃入口 QR code **不可成為員工**。
- 允許同一人加入多企業、多部門／分店，並明確切換企業；每次 API 寫入均驗證所選 `tenant_id` + 角色權限。
- 支援停權、離職、邀請到期、撤銷 LINE 綁定與重新綁定；離職後保留法定出勤歷史，不再允許登入該企業。
- 未授權 LINE 通知、封鎖 OA、超過訊息配額時，Web App 仍可正常操作，通知改顯示站內收件匣；通知發送與實際送達狀態分開記錄。

### 2.3 介面流

```text
員工接收邀請 → LINE／瀏覽器登入 → 綁定企業／部門 → 我的今日班表
     ├─ 上班打卡／下班打卡
     ├─ 我的班表／可上班時段／排休／換班
     ├─ 請假／加班／補卡／異常申訴
     ├─ 工時、假期餘額、歷史紀錄
     └─ LINE 訊息與站內通知

主管登入 → 團隊今日人力 → 週／月排班 → 審核中心
          → 異常處理 → 工時與假勤報表

企業 HR → 組織設定 → 人員聘僱／權限／班型與假別
        → 規則與地點設定 → 跨店管理 → 月結鎖定 → 匯出

平台後台 → 企業與方案管理 → OA 綁定狀態 → 安全稽核／通知配額
```

| HR-RPT-04 | MUST | 月結試算 → 異常補正 → 確認鎖定 → 匯出；鎖定後只能以有權限調整單與更正報表處理 |
| HR-RPT-05 | MUST | 員工可取得本人出勤資料；系統可輸出完整變更歷程供勞檢或依法提出 |
| HR-RPT-06 | SHOULD | 人力成本預估（時薪／工時計算基礎，不等於正式薪資核發）、API 或匯出介接薪資系統 |

### 3.7 平台營運（HR-OPS）

- 多企業試用／訂閱／席位數／分店方案與配額管理（系統架構先保留，計費規格另行設定）。
- 每家企業可設定品牌、LOGO、假別、班制、規章、打卡點與 OA 串接；其他企業不受影響。
- 平台客服與問題回報需能關聯租戶、操作追蹤 ID；不得在客服畫面默認暴露敏感員工個資。
- 備援匯出、企業停用、合法保存期限到期後刪除／匿名化流程。
- 測試企業與測試帳號可在 **Demo 模式**一鍵進入，不需先購買與輸入真實 LINE token；正式模式不允許繞過伺服器驗證。
- 測試資料須與正式資料隔離，重跑部署／測試不得清空現有企業與員工資料。

## 5. 重要狀態機與業務規則

### 5.1 班表

`DRAFT → PUBLISHED → SUPERSEDED / CANCELLED`；發布後編輯需產生新版本，保留舊版及通知差異。刪除已發布的班表不可破壞歷史工時。

### 5.2 出勤

每次打卡建立不可變 `PunchEvent`（`IN` / `OUT` / `BREAK_START` / `BREAK_END`）。歸屬班別時不可只依日曆日切分，需處理跨午夜與跨日。異常狀態可為 `NORMAL / LATE / EARLY / MISSING / UNMATCHED / PENDING_CORRECTION`，狀態可重算但原事件不可改寫。

### 5.3 請假／補卡／加班／換班

`DRAFT → SUBMITTED → APPROVED / REJECTED / WITHDRAWN / CANCELLED`，多層審核於 `SUBMITTED` 下保存各層紀錄。換班需被換班者接受與主管核准後才生效；請假核准才扣核可使用的假額；同一申請重送不得重扣。

### 5.4 工時

- **實際出勤時間、企業核認工時、法定加班判定、預估薪資工時**須分開保存與呈現。
- 不得把「請假已核准」「加班未申請」「定位失敗」當作刪除原始上下班紀錄的理由。
- 跨月／跨年夜班、休息時間、國定假日、不同聘僱身份與變形工時須可由企業規則處理；法令適用性未確認時顯示警示，不產生虛假的「合法」結論。

## 9. 法令、隱私與資料治理（臺灣）

- 依《勞動基準法》第 30 條，雇主須保存出勤紀錄 **五年**，逐日記載至**分鐘**，員工申請副本或影本不得拒絕。系統 MUST 支援這些能力，包含員工離職、企業停用、資料備份與合法匯出。
- 系統 SHALL 保留實際出勤原始紀錄與每次更正的軌跡，不以排班、核准狀態代替真實出勤事實；出勤資料保存到期前避免硬刪除。
- 假別、特休、加班、輪班與休息制度依適用法令及協議設計可配置規則，正式推出前需請熟悉臺灣勞動法規者審核；不能把任何提示當作法律上的自動核可。
- GPS 在按下打卡且明確告知目的後才取用，**不做背景連續追蹤**；儘量避免長期保存高精度定位歷史，採必要最小化、權限隔離、保存與刪除政策。具敏感性的請假證明附件以嚴格權限保護。
- 含個資資料皆須有加密傳輸、適當靜態加密、備份與復原、存取日誌、資料主體權利處理流程；政府查核／員工查詢的資料匯出需具備追蹤紀錄。

## 10. 技術方案建議（尚未定案）

- **架構**：專案 `workforce-management/` 獨立前後端、資料庫 schema、環境變數、部署、測試與 CI；共用工具程式碼必須採明確套件介面而非直接存取其他產品的資料表。
- **前端**：Next.js + TypeScript、Responsive Web UI；LIFF 作為入口而非唯一的瀏覽器模式。
- **後端**：Next.js API 或獨立服務 + PostgreSQL；交易／約束確保打卡、核准與假額扣減一致性；排程與訊息佇列處理提醒。
- **LINE**：LIFF、LINE Login、Messaging API、Rich Menu；密鑰在伺服器環境變數／Secrets，前端不得暴露 Channel secret 或 access token。
- **認證**：短效 Session、HTTP-only cookie、CSRF 防護、Rate limit、審計；正式資料與 Demo／測試租戶隔離。
- **通知成本**：預設觸發式＋批次／摘要，而非高頻推播；不得假設 Messaging API 配額無限或訊息一定送達。
- **定位風險**：GPS 可遭模擬與漂移，只能作為佐證；可搭配短效動態 QR、門市核准及異常人工複核，禁止宣稱絕對防代打卡。
- 對高併發多企業應以 `tenant_id` 複合索引、時間範圍查詢、分頁、背景報表與監控來擴充；需完成負載測試後才能宣稱擴充數量。

## 11. 非功能性需求（NFR）

1. 核心員工手機頁面目標互動回應 p95 < 2 秒（不含外部 LINE 授權與使用者定位等待）；長報表非同步產生。
2. 打卡／簽核操作採唯一冪等鍵與資料庫交易：重送、不穩定網路、雙擊不能生成重複事實。
3. 全站繁體中文優先、手機與桌機同版響應式；無障礙、鍵盤操作、明確錯誤與成功回饋。
4. 上／下班打卡或請假送出後，頁面顯示**伺服器回傳已成功**才能宣稱成功。
5. 權限測試至少覆蓋跨公司、跨分店、離職員工、主管越權、LINE Provider 切換及失效邀請。
6. 升級部署不得覆蓋正式店家或測試資料；資料庫遷移可回復，備份還原須演練；所有敏感變更記錄審計。
7. 重要通知需要有站內備援；LINE 訊息發送失敗不影響請假／出勤交易成功。
8. 異常提示儘量顯示可操作資訊，例如「定位失敗，請補卡」而非大量開發者專用的 Debug 訊息。
9. 出勤紀錄滿足保存及可匯出需求，企業停止訂閱後也需有符合法令的保存、取回與刪除政策。
10. 安全事件具備告警、權限撤回、憑證輪替、事故追蹤機制。

## 13. 風險與待確認產品決策

1. **LINE OA 模式**：平台總公司 OA 與企業自有 OA 同時支援；後續需決定自有 OA 綁定流程、審核、維運責任、收費與官方 API 額度。
2. **法遵**：不同產業、工時制度與特殊身分規定不同；正式上線前應進行專業勞動法規審核與可配置政策驗證。
3. **隱私**：定位、健康相關假別、附件的蒐集必要性、同意／告知、存取及保存策略需形成正式隱私文件。
4. **多個 LINE Provider**：不同企業 OA 可能讓使用者的外部識別不同，須提供可靠且防冒領的帳號連結／重新綁定流程。
5. **AI 指令**：只能協助填單，不能直接單憑模型文本產生已打卡或已核准事實。
6. **資料隔離**：其他 LINE 產品的「商家」不預設等於本產品「雇主」，不自動複用既有店家／顧客資料。
7. **銷售模型**：依公司／分店／在職員工人數／LINE 訊息量計費尚待定價測試；不先綁死計費方式。
8. **技術授權**：借鑑 GitHub 專案的功能模式，不代表可直接複製代碼；導入須先確認具體版本、LICENSE 與相依套件義務。
