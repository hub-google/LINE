## 文件使用方法與狀態

| 標示 | 定義 | 驗收方式 |
|---|---|---|
| **A：已具備程式與既有驗收依據** | UI 與 DB／RPC 存在，且過往 QA 報告有相應成功紀錄 | 正式發布仍需重新回歸；不可將「已有證據」理解為本次所有子情境均重測 |
| **B：已有入口／後端，仍須個別實機驗收** | 有 UI 與部分 DB／服務設計，但尚缺完整真機／實信／外部 API 或邊界測試 | 逐步操作，保存伺服器回應與 UI 截圖；若失敗即列缺陷 |
| **C：PRD 需求，未完成端到端交付** | 產品要求存在，但尚未完成端到端實作或重要外部依賴 | 不可列為可售功能；需開發、測試與證據 |
| **N：非本期產品範圍** | 已明訂為非目標（例如直接薪資核發） | 若擬擴張產品範圍，先修改 PRD，再另行開發 |

**測試基礎**：優先使用虛構企業「Workforce QA 星河服務股份有限公司」與「Workforce QA 海角工作室」，角色包括 Owner、HR、王營運經理、林門市組長、張一凡／李小晴、客服主管及客服員工。真實帳號與個人資料不得放入共用 DEMO。測試狀態與佐證可對照 [`ORG_HIERARCHY_RESULTS_20261109.md`](./ORG_HIERARCHY_RESULTS_20261109.md)、[`QA_E2E_STATUS_20261105.md`](./QA_E2E_STATUS_20261105.md)、[`IMPLEMENTATION-STATUS.md`](./IMPLEMENTATION-STATUS.md)；後者含歷史紀錄，存在部分過時敘述，應以最新實際程式碼和 DB 為準。

**驗收統一規則**：每案必須記錄測試角色、測試企業、操作起訖時間、重要畫面、預期／實際結果、資料庫或 RPC 證據、PASS／FAIL／BLOCKED、缺陷連結。未執行的不能填 PASS。以 `America/*` 或系統時區猜測日期不可接受，顯示採 `Asia/Taipei`，原始事件保留 UTC 時間。注意提交與重試的冪等性、企業隔離及個資最小揭露。

## 角色故事（端到端主線）

### 使用旅程 A：新公司從零開通到第一天正式打卡
1. Owner 註冊並驗證 Email（AUTH-02），建立新公司（AUTH-03）。
2. 建兩個門市（ORG-01）與部門（ORG-02），邀請 HR、經理、組長與員工（ORG-03、ORG-04）。
3. 員工從專屬連結加入（AUTH-09）；Owner 編三層主管樹（ORG-06），各角色登入核對可見範圍（ORG-07、OPS-01）。
4. HR 設置假別政策及額度（LVE-11）；主管建立班型與最低人力需求（SCH-06、SCH-10）。
5. 員工提交可上班／排休時段（SCH-08、SCH-09），主管預覽草稿、修正並發布（SCH-12、SCH-03）。
6. 員工於實際上班日 IN、休息、OUT（ATT-01～03），查出勤紀錄（RPT-02）。
7. HR 在報表檢查無缺卡、留存稽核後完成行政試算（RPT-05）。
**終局驗證**：員工能看到本人班表、所有資料落在正確 tenant；不代表薪資法遵自動核定。

### 使用旅程 B：兼職人員臨時不能上班，改由他人代班
1. 兼職張一凡查看已發布班（SCH-01），發現週六行程衝突。
2. 張提出換班，指定李小晴已發布班（SCH-16）。
3. 李以自己的 Auth 身分同意，班表仍保留原樣（SCH-17）。
4. 林組長檢查休息與管理鏈、核准換班（SCH-18）。
5. 兩人分別查看班表與通知（LINE-01），主管核對修訂歷程。
**反面測試**：李拒絕時不得換班；張不能替李同意；同一班不能被重複交換。

### 使用旅程 C：員工忘記打卡並提出補卡
1. 主管已發布昨日班次，但張一凡未留下 IN（ATT-11）。
2. 主管掃描已完成班次，出現缺卡異常（ATT-12）。
3. 張從獨立「補卡」入口申請，填漏卡區間與原因（LVE-05）。
4. 林組長核准或駁回（LVE-08、LVE-09），必要時記錄異常結案（ATT-13）。
5. HR 重新查打卡明細及行政工時（RPT-01、RPT-03）。
**終局驗證**：原始缺卡事件不被偽造成真實 IN；所有修正有明確分表與歷程。

### 使用旅程 D：從請假到月結
1. HR 定義假別政策、生效日及員工額度（LVE-11）。
2. 李小晴請假（LVE-01），系統先占用待審額度（LVE-12）。
3. 王經理處理申請，李收到站內通知（LVE-08、LINE-01）。
4. 月底主管掃描遲到／早退／缺卡（ATT-12），HR 核對補卡和異常。
5. HR 月工時試算（RPT-05），確認後鎖定（RPT-07）。
6. 發現事後正當更正，必須新增調整單（RPT-08），原月結快照不覆寫。
**終局驗證**：假額度不得雙扣，月結可追溯且不將行政試算直接當法定薪資。

### 使用旅程 E：同一人任職兩家公司
1. 同一個 Email/Auth UUID 分別接受 A、B 公司邀請（AUTH-07、AUTH-09）。
2. 切換 A 公司檢查班表與同事資料，切換 B 公司再檢查（AUTH-07）。
3. A 公司主管嘗試存取 B 公司員工或審核申請（OPS-01、LVE-15）。
4. 兼職本人在 A、B 各有不同時段打卡（ATT-01）；確認不串資料。
5. 針對同時段重複排班執行 SCH-19，**目前列為待交付驗收**，不能宣稱已有跨公司隱私保護式衝突處理。
**終局驗證**：租戶隔離優先於便利，不揭露另一公司的商業或員工資料。

### 使用旅程 F：LINE 身分、通知與退場
1. 正式員工從網頁登入並查站內通知（LINE-01、LINE-02）。
2. 平台 Channel 實際配置後，以 LIFF 驗證並綁定（LINE-03）。
3. 主管發布班表／審核，觸發站內事件；HR 查看推播處理狀態（LINE-05、LINE-06）。
4. 員工解除綁定再驗證重綁（LINE-04）；確認不會對舊身分送訊息。
5. 企業自有 OA、Flex Message 與費用控制列 LINE-07～09，**目前仍是缺口**，須單獨部署並實機驗收。
**終局驗證**：Edge Function 存在、API 發送成功與 LINE 已實際送達是三種不同狀態，不能混為一談。

## 01｜首次使用、帳號與企業切換

註冊、登入、邀請、密碼、租戶工作空間。本節共 9 案。

### AUTH-01｜訪客進入公開 DEMO（A）

**執行者**：訪客。**起始條件**：未登入；共用虛構測試企業。

**操作**：
   1. 開啟網站
   2. 辨識「公開 DEMO」與測試環境提示
   3. 進入總覽、切換排班與打卡頁

**預期**：不要求先註冊；顯示虛構員工、班次與打卡紀錄；不能將 DEMO 當正式企業

**例外／權限驗證**：在共用 DEMO 不輸入真實個資；其他訪客可能同時修改資料

### AUTH-02｜新企業擁有者註冊（A）

**執行者**：企業擁有者。**起始條件**：使用新的測試 Email，尚無企業。

**操作**：
   1. 右上「企業登入」
   2. 選「註冊」填 Email／密碼
   3. 依 Supabase 郵件設定完成信箱驗證
   4. 使用帳密登入

**預期**：取得自己 Auth UUID；尚未加入其他企業；可以建立自己的企業

**例外／權限驗證**：未驗證信箱、重複 Email 或 Supabase 密碼政策不符時不冒稱成功

### AUTH-03｜建立第一家企業（A）

**執行者**：企業擁有者。**起始條件**：已登入但尚未加入企業。

**操作**：
   1. 在空企業頁點「建立企業」
   2. 輸入公司名稱
   3. 提交後刷新
   4. 檢查工作空間名稱及成員身分

**預期**：產生獨立 tenant；建立者為 Owner，不能因此取得別家權限

**例外／權限驗證**：建立失敗時不顯示假資料；請求重送不得產生重複公司

### AUTH-04｜帳密錯誤與登入過期（B）

**執行者**：全體正式使用者。**起始條件**：已有企業帳號。

**操作**：
   1. 輸入錯誤密碼
   2. 確認錯誤訊息
   3. 再以正確資料登入
   4. 模擬 access token 過期並刷新頁面

**預期**：錯誤登入不得讀取正式資料；可用 refresh token 續期，無法續期則重新登入

**例外／權限驗證**：不可把 refresh token／JWT 記錄至公開畫面或錯誤訊息

### AUTH-05｜忘記密碼寄信（B）

**執行者**：全體正式使用者。**起始條件**：有已驗證信箱；Auth 郵件服務可用。

**操作**：
   1. 登入視窗點「忘記密碼」
   2. 填寫 Email
   3. 送出
   4. 檢查自己信箱

**預期**：若帳號存在可收到 Supabase 重設信；畫面不透露此 Email 是否註冊

**例外／權限驗證**：須確認 Supabase Redirect URL 白名單含正式 Pages 網址；此次尚未執行實信箱回跳測試

### AUTH-06｜經重設連結設定新密碼（B）

**執行者**：全體正式使用者。**起始條件**：持有有效且未過期的 recovery link。

**操作**：
   1. 點 Email 連結返回網站
   2. 系統驗證 recovery access token
   3. 輸入兩次相同新密碼
   4. 更新後重新登入

**預期**：密碼由 Supabase Auth 更新；URL 中的 token 立即清除；舊頁面登入狀態清除

**例外／權限驗證**：無效／逾期連結、兩次密碼不一致、弱密碼依 Supabase 規則被拒絕

### AUTH-07｜單一帳號切換兩家公司（A）

**執行者**：跨公司兼職員工。**起始條件**：同一 Auth UUID 已受邀加入兩個不同企業。

**操作**：
   1. 登入平台
   2. 在右上「選擇公司」切換 A 公司與 B 公司
   3. 分別打開班表、請假及通知
   4. 切回 A 公司

**預期**：每次僅查所選 tenant 的合法資料；切換時不殘留前一家資料

**例外／權限驗證**：不可把 A 公司的申請或打卡寫進 B 公司；UI 與 RLS 都須阻擋

### AUTH-08｜登出與重新登入（A）

**執行者**：全體正式使用者。**起始條件**：已登入企業模式。

**操作**：
   1. 點右上「登出」
   2. 確認回到公開 DEMO／未登入
   3. 重新進入企業登入
   4. 以其他測試帳號登入

**預期**：清除 sessionStorage 正式登入狀態；不沿用前一人的公司或角色

**例外／權限驗證**：瀏覽器返回上一頁不得還原前一用戶的私有資料

### AUTH-09｜手機打開企業邀請網址（A）

**執行者**：受邀員工。**起始條件**：Owner 已產生綁定指定 Email 的一次性連結。

**操作**：
   1. 從手機開啟邀請
   2. 若未登入先註冊或登入同一 Email
   3. 完成驗證並接受邀請
   4. 開啟組織頁

**預期**：受邀者進入正確 tenant；角色及主管由邀請記錄決定

**例外／權限驗證**：錯誤 Email、過期 7 日、已使用 token 與其他租戶都不得綁定


## 02｜企業架構、員工與權限

Owner、HR、主管、組長、員工及跨分店人事操作。本節共 16 案。

### ORG-01｜建立分店（A）

**執行者**：Owner／HR。**起始條件**：企業已建立。

**操作**：
   1. 開啟「員工與分店」
   2. 選「新增分店」
   3. 輸入不同分店名稱並儲存
   4. 回清單檢查

**預期**：新分店只屬於目前 tenant；可供排班、GPS、QR 管理使用

**例外／權限驗證**：員工不得操作；跨企業不可建立分店

### ORG-02｜建立部門與隸屬門市（A）

**執行者**：Owner／HR。**起始條件**：企業已有分店。

**操作**：
   1. 開啟「組織與權限」或員工設定中的部門區
   2. 新增部門、選分店
   3. 儲存後回組織頁

**預期**：部門只出現在本企業；員工可指派到所屬部門

**例外／權限驗證**：不能把其他公司的分店 ID 當成自己分店

### ORG-03｜Owner 邀請一般員工（A）

**執行者**：Owner。**起始條件**：已建立分店；有虛構 Email。

**操作**：
   1. 組織與權限→「邀請員工」
   2. 填 Email、姓名、職稱、部門、分店、角色
   3. 產生連結並安全轉傳

**預期**：產生 7 天有效、指定 Email 的一次性邀請，不直接替員工設密碼

**例外／權限驗證**：邀請 Token 應只在授權者視窗顯示，不可放在公開日誌

### ORG-04｜邀請主管或人資（A）

**執行者**：Owner。**起始條件**：企業有兩個部門。

**操作**：
   1. 為人員選 manager 或 HR 角色
   2. 指定其直屬上級
   3. 由受邀人接受
   4. 登錄後驗證畫面和資料權限

**預期**：Owner 可以設定 HR；Manager 範圍依 reports_to，不是任意全公司

**例外／權限驗證**：一般主管不能自行新增 HR 或 Owner

### ORG-05｜人資建立員工邀請（A）

**執行者**：HR。**起始條件**：HR 已完成授權。

**操作**：
   1. 以 HR 帳號開組織頁
   2. 建立一般員工／主管邀請
   3. 檢查角色清單
   4. 企圖修改 Owner 權限

**預期**：可管理一般人員；不可改 Owner，也不可任意提升 HR／Owner

**例外／權限驗證**：伺服器端 RPC 必須拒絕越權，即使修改前端欄位亦然

### ORG-06｜設定三層主管鏈（A）

**執行者**：Owner。**起始條件**：已建立營運經理、門市組長、一般員工。

**操作**：
   1. 王經理指派給 Owner
   2. 林組長指派給王經理
   3. 張員工指派給林組長
   4. 用三人個別登入

**預期**：王可管理林與張；林只能管理張；張僅查本人

**例外／權限驗證**：不可把自己設為上級；不可形成循環關係

### ORG-07｜跨部門主管看不到他組（A）

**執行者**：營運經理／客服主管。**起始條件**：兩部門各有主管與下屬。

**操作**：
   1. 營運經理查看名冊及審核中心
   2. 再切客服主管獨立帳號
   3. 比較可見人員

**預期**：只能顯示管理鏈下的人；平行主管不能跨部門查閱

**例外／權限驗證**：直接修改 URL、tenant_id 或 RPC 參數不應繞過 RLS

### ORG-08｜員工不可以修改自己的角色（A）

**執行者**：一般員工。**起始條件**：員工已加入企業。

**操作**：
   1. 檢查組織頁沒有管理控制
   2. 以員工 JWT 呼叫角色變更 RPC（測試環境）
   3. 重新載入

**預期**：角色、主管鏈與角色稽核不變；伺服器拒絕

**例外／權限驗證**：不能只靠隱藏按鈕防止提升權限

### ORG-09｜調整員工的直屬主管（A）

**執行者**：Owner／HR。**起始條件**：員工目前屬於 A 組。

**操作**：
   1. 設定層級→改為 B 組主管
   2. 儲存
   3. 讓 A 與 B 主管各自登入查名冊與審核

**預期**：RLS 依新主管鏈即時生效；歷程寫入稽核

**例外／權限驗證**：已處理的歷史申請不可因此隱藏或遭擅自改寫

### ORG-10｜員工在職與停用（B）

**執行者**：Owner／HR。**起始條件**：測試員工已建檔。

**操作**：
   1. 進入「員工與分店」員工設定
   2. 停用員工
   3. 再查排班、打卡、邀請與主管清單

**預期**：停用狀態保留歷史資料，依規則阻止新打卡或新排班

**例外／權限驗證**：不可刪除曾發生的打卡與核准軌跡；復職須確認權限

### ORG-11｜員工 CSV 批次新增（B）

**執行者**：Owner。**起始條件**：備有 UTF-8 CSV 虛構員工名單。

   2. 重新匯入
   3. 核對原姓名、角色、分店

   4. 排 B 店班

**預期**：有效期間可依規則排 B 店班；逾期或未授權不可任意跨店

**例外／權限驗證**：B 店所屬企業必須相同；不跨 tenant 發授權

### ORG-14｜員工技能與證照排班（C）

   2. 建立需要證照的班段
   3. 執行自動排班

**預期**：資料模型已有 skills 欄位，但管理、查核與自動排班完整規則仍需完成

   2. 處理未來班次與待審件
   3. 試圖打卡
   4. 恢復在職時檢查重新授權

**預期**：需保存歷史、限制新操作且不遺失過往工時；目前未完成完整生命週期 UX

**例外／權限驗證**：不可直接清空該員工全部紀錄

### ORG-16｜公司停用與資料交接（C）

   3. 處理成員存取及 LINE 通知

**例外／權限驗證**：需資料保存政策與不可逆操作雙重確認


## 03｜排班、班型、換班與人力需求

日週月、草稿發布、跨日、衝突、偏好與自動建議。本節共 20 案。

**操作**：
   1. 進排班管理
   2. 看本週日期
   3. 使用上週／下週／今天
   4. 核對自己的班次

**預期**：不會看到無權限的其他員工個資；草稿與已發布的標示明確

**例外／權限驗證**：時間依台灣時區，不得把跨日班切錯日期

**執行者**：主管。**起始條件**：員工及分店已建立。

   2. 選人員、分店、上班和下班時間
   3. 選草稿／立即發布
   4. 送出

**預期**：產生 wm_shifts 班次且可由員工查閱已發布班次

**例外／權限驗證**：起訖反向、非本人管理範圍、其他租戶員工不得成功

### SCH-03｜草稿審閱再發布（A）

**執行者**：主管。**起始條件**：已存在一筆 draft 班次。

   1. 排班明細找到草稿
   2. 查核人員與時間
   3. 點「發布」
   4. 員工重新開班表

**預期**：發布後班次狀態切為 published，保留資料庫事件

**例外／權限驗證**：發布時重新查衝突與企業排班規則，不能只靠建立草稿時的檢查

### SCH-04｜班次取消與保留歷史（A）

**執行者**：主管。**起始條件**：已發布但尚未開始的班次。

**操作**：
   1. 班表明細選「取消班次」
   2. 確認
   3. 員工刷新
   4. 再查稽核歷史

**預期**：班次標記 cancelled 且不再當有效排班，不得硬刪歷史

**例外／權限驗證**：不可取消已月結而造成快照不一致

### SCH-05｜重疊班次拒絕（A）

**執行者**：主管。**起始條件**：同員工 09:00–18:00 已有班次。

**操作**：
   1. 新增同日 12:00–20:00
   2. 送出
   3. 檢查失敗訊息和原班表

**預期**：拒絕重疊，不偷偷建立第二班

**例外／權限驗證**：跨午夜、秒級邊界與同分店／不同分店同樣檢查

### SCH-06｜固定班型範本（B）

**執行者**：主管。**起始條件**：有早班及晚班常用模板。

**操作**：

   2. 新增班次時選範本
   3. 查表單自動帶入時間

**預期**：主管可調整範本所帶時間；跨日範本須帶出隔日日期

**例外／權限驗證**：儲存後仍由 DB 確認期間合法；範本不是已發布班表

### SCH-07｜跨日夜班（B）

**執行者**：主管／夜班員工。**起始條件**：夜班從 22:00 至次日 06:00。

**操作**：
   1. 建立夜班模板
   2. 新增本日 22:00 到隔日 06:00
   3. 員工查班
   4. 次日下班打卡

**預期**：班次保留完整實際日期時間，報表不漏掉隔日離場

**例外／權限驗證**：不能把同一天 06:00 當成早於 22:00 的無效時間

### SCH-08｜員工填可上班時間（B）

**執行者**：兼職員工。**起始條件**：本週尚未排班。

**操作**：
   1. 進排班→「提供可上班時段」
   2. 輸入週五 18:00–22:00 並選可上班
   3. 送出

**預期**：資料庫保留員工偏好，主管排班建議可採用

**例外／權限驗證**：不能替別家公司或其他員工提交個人偏好

### SCH-09｜員工提出排休（B）

   2. 選「不可上班／排休」
   3. 填區間與理由
   4. 回到排班頁查看

**預期**：自動建議避免選入該區間；正式已發布班次需另走換班／主管處理

**例外／權限驗證**：不可把排休直接當已核准請假

### SCH-10｜設定最低人力（B）

**執行者**：門市主管。**起始條件**：餐飲店尖峰需至少 3 人。

   2. 再查看排班建議

**預期**：需求作為建議演算法輸入，無人可排時列缺口

**例外／權限驗證**：不可用虛構員工填滿需求

### SCH-11｜複製本週到下週草稿（B）

### SCH-12｜自動排班預覽與確認（B）

**執行者**：主管。**起始條件**：已有最低人力需求與可工作時段。

   4. 再次看班表

## 04｜上下班打卡、GPS、QR 與異常

員工實際出勤，資料庫以伺服器時鐘記錄。本節共 15 案。

### ATT-01｜一般上班打卡（A）

**預期**：由 DB 產生時間與一筆 IN 事件；正式用戶不得替別人打卡

**例外／權限驗證**：網路錯誤時不能顯示成功，也不能偽造打卡時間

   1. 按「休息開始」
   2. 用餐後按「休息結束」
   3. 查當日事件列表

**例外／權限驗證**：重複休息、不合狀態順序由伺服器規則判斷；報表不能草率當成完整法定休息核算

### ATT-03｜正常下班打卡（A）

   1. 按「下班打卡」
   2. 查最近打卡列表
   3. 到工時報表查當日成對紀錄

**預期**：記錄 OUT，可與 IN 配對產生行政試算工時

**例外／權限驗證**：無 IN 的孤立 OUT 應被標示不完整，不得憑空補出 IN

### ATT-04｜快速連點與冪等重送（A）

**執行者**：員工。**起始條件**：瀏覽器或網路可能重送打卡請求。

   1. 連點上班打卡
   2. 以相同請求識別碼重送
   3. 查 DB 事件數

**預期**：同一請求不應新增第二筆有效事件；有防連續重複政策

**例外／權限驗證**：不能因按鈕動畫完成就假定伺服器寫入成功

### ATT-05｜沒有網路與伺服器失敗（B）

**執行者**：員工。**起始條件**：切離網路或暫時失去 API。

**操作**：
   1. 按上班打卡
   2. 觀察錯誤
   3. 恢復網路
   4. 重新進頁確認是否有紀錄

**預期**：明確顯示未成功，不做離線假打卡

**例外／權限驗證**：重試前須先查有無成功入庫，避免重複

### ATT-06｜GPS 必填門市（B）

**執行者**：員工／HR。**起始條件**：HR 設定門市經緯度及容許半徑。

**操作**：
   1. HR 啟用 GPS 必填
   2. 員工允許定位
   3. 在合法範圍點上班打卡
   4. 查看事件

**預期**：定位資訊由瀏覽器同意提供，DB 驗證半徑與精度

**例外／權限驗證**：沒有授權或超過半徑時不能直接通過

### ATT-07｜GPS 被拒或訊號漂移（B）

**執行者**：外勤員工。**起始條件**：門市 GPS 必填。

**操作**：
   1. 拒絕瀏覽器定位
   2. 再於範圍外打卡
   3. 提交補卡申請及原因

**預期**：拒絕或漂移時顯示原因及補卡途徑，避免偽造打卡

**例外／權限驗證**：不得為了順利演示自動注入假 GPS

### ATT-08｜主管產生 90 秒 QR（B）

**執行者**：主管。**起始條件**：正式企業已啟用 QR 打卡。

**操作**：
   1. 選「動態 QR」
   2. 選門市
   3. 按「產生 90 秒 QR」
   4. 在現場螢幕展示

**預期**：顯示短效 QR 與失效時間，僅屬已授權門市

**例外／權限驗證**：公開 DEMO 不應發出可在正式企業打卡的 token

### ATT-09｜員工掃描 QR 打卡（B）

**執行者**：員工。**起始條件**：已登入；持有有效短效 QR。

**操作**：
   1. 用手機掃 QR 開啟網站
   2. 確認所屬企業
   3. 按 IN／OUT
   4. 查打卡紀錄

**預期**：後端核對短效憑證與本人身分，再記錄伺服器時間

**例外／權限驗證**：他公司 QR、過期 QR、重放與停用的 QR 不得通過

### ATT-10｜QR 是否可取代 GPS（B）

**執行者**：Owner／HR。**起始條件**：門市既有 GPS 政策。

**操作**：
   1. 打開 QR 安全設定
   2. 測試「可替代 GPS」關閉與開啟
   3. 員工在沒有 GPS 時掃碼

**預期**：只在明確授權的門市政策下 QR 才可能替代 GPS

**例外／權限驗證**：QR 不是 GPS，也不能據此推論人確實位於某個座標

### ATT-11｜漏打上班卡（A）

**執行者**：員工／主管。**起始條件**：已排班但當日缺 IN。

**操作**：
   1. 員工按「補卡」
   2. 選漏上班卡、日期區間、原因
   3. 主管在審核中心核准或駁回

**預期**：原始打卡不被覆寫；補正形成獨立更正與稽核資料

**例外／權限驗證**：未核准不視作已有原始 IN 事件

### ATT-12｜出勤異常定期掃描（B）

**執行者**：主管。**起始條件**：前幾天有結束的班次及出勤事件。

**操作**：
   1. 前往「出勤異常」
   2. 選起訖期間
   3. 按掃描已完成班次
   4. 檢查遲到、早退、缺卡

**預期**：伺服器只掃描已結束班次；重掃不重複建立同一案件

**例外／權限驗證**：掃描期間不得超過 DB 允許範圍；已核准整班請假不當缺卡

### ATT-13｜出勤異常結案（B）

**執行者**：主管。**起始條件**：有一筆未結案異常。

**操作**：
   1. 在異常清單按「結案」
   2. 填補卡處理結果／理由
   3. 送出
   4. 重整後查案件

**預期**：open 改 resolved，保留結案原因與原始紀錄

**例外／權限驗證**：不能直接更改原始打卡時間；他部門主管不應代結案

### ATT-14｜自訂遲到容許及處理期限（B）

**執行者**：Owner／HR。**起始條件**：企業已建立。

**操作**：
   1. 到出勤異常設定容許分鐘、SLA、靜音時間
   2. 儲存
   3. 掃描舊班次

**預期**：企業自己的一套規則生效；不同企業不受影響

**例外／權限驗證**：不是所有企業都適用同一法定遲到扣薪規則

### ATT-15｜外勤、共用設備、離線補傳（C）

**執行者**：外勤員工／現場主管。**起始條件**：特殊工作地點或共享平板。

**操作**：
   1. 建立合法外勤免 GPS 流程
   2. 主管代登記並記操作者
   3. 網路中斷後補送事件
   4. 核對稽核

**預期**：須明確同意及權限；防冒名與重送，保留原始發生時間

**例外／權限驗證**：目前外勤例外及完整共用設備代登記流程未驗收完成


## 05｜請假、加班、補卡、換班與簽核

三個獨立入口、額度政策、多層審核與私有附件。本節共 17 案。

### LVE-01｜員工請特休（A）

**執行者**：員工。**起始條件**：企業已有有效假別政策和可用時數。

**操作**：
   1. 進「差勤申請」按獨立「請假」
   2. 選假別、起訖時間、理由
   3. 確認送出
   4. 回申請紀錄

**預期**：產生本人 pending 申請，依規則計入待審占用

**例外／權限驗證**：沒有額度或起訖反向應拒絕，不可偷偷扣成負數

### LVE-02｜病假與證明附件（B）

**執行者**：員工／主管。**起始條件**：假別政策設為需證明。

**操作**：
   1. 請病假並送出
   2. 在申請證明附件區上傳授權 PDF／JPG／PNG
   3. 主管查看附件
   4. 審核

**預期**：檔案保存在私有 Storage，只有申請本人與授權主管可下載

**例外／權限驗證**：不能將醫療證明放公開 URL；檔案大小與類型須限制

### LVE-03｜員工申請加班（A）

**執行者**：員工。**起始條件**：有當天已發布班次。

**操作**：
   1. 點獨立「加班」
   2. 選開始/結束時間、事由
   3. 檢查預計時數
   4. 送出

**預期**：產生 overtime pending；預計時數不等於實際加班或已核薪

**例外／權限驗證**：單次超過 24 小時、結束早於開始必須阻止

### LVE-04｜跨午夜加班（B）

**執行者**：員工。**起始條件**：加班從晚上 22:00 到隔日 01:00。

**操作**：
   1. 選今日 22:00
   2. 結束日期選次日 01:00
   3. 確認顯示三小時
   4. 送出

**預期**：顯示三小時的區間，不當成同一天負數

**例外／權限驗證**：不得因跨午夜漏掉結束日期或自動判定核准時數

### LVE-05｜員工補上班卡／下班卡（A）

**執行者**：員工。**起始條件**：出勤事件不完整。

**操作**：
   1. 點獨立「補卡」
   2. 選漏上班／漏下班／雙向漏卡／出勤更正
   3. 填區間與理由送出

**預期**：申請與原始事件分表保存；等待主管審核

**例外／權限驗證**：補卡表單不應混入假別下拉欄位

### LVE-06｜申請紀錄依類型切換（A）

**執行者**：員工／主管。**起始條件**：已有請假、加班、補卡資料。

**操作**：
   1. 在差勤申請切「全部／請假／加班／補卡」
   2. 查看每筆狀態與理由

**預期**：各類型筆數及清單對應，不會混淆申請類別

**例外／權限驗證**：不同角色僅能查看 RLS 允許的紀錄

### LVE-07｜員工撤回待審申請（B）

**執行者**：員工。**起始條件**：本人一筆 pending 尚未審核。

**操作**：
   1. 在待審申請區找到本人案件
   2. 按「撤回」
   3. 確認
   4. 再進主管待審清單

**預期**：撤回後不可再被主管核准；保留撤回歷程

**例外／權限驗證**：已核准或他人申請不能走此入口撤回

### LVE-08｜直屬組長核准（A）

**執行者**：組長。**起始條件**：直屬員工已請假。

**操作**：
   1. 組長登入審核中心
   2. 確認是自己管理鏈下的員工
   3. 點「核准」
   4. 員工重新登入

**預期**：狀態變 approved，留操作時間並通知員工

**例外／權限驗證**：不能審核組長自己的申請或其他主管的員工

### LVE-09｜主管駁回有原因（A）

**執行者**：主管。**起始條件**：員工送出加班但缺事由證據。

**操作**：
   1. 主管開審核中心按「駁回」
   2. 查決定備註
   3. 員工在申請歷史與通知查看

**預期**：變 rejected，原始申請保留，不能當已完成工時

**例外／權限驗證**：已駁回不能再次核准同一筆為相同操作

### LVE-10｜兩層／三層主管審核（B）

**執行者**：組長／經理／HR。**起始條件**：正式企業假別設定多層簽核。

**操作**：
   1. 員工送假
   2. 第一層主管核准
   3. 檢查仍須下一層
   4. 第二層不同主管核准
   5. 員工看最終結果

**預期**：未走完規定層數不得提前列最終核准

**例外／權限驗證**：不能由同一個人重複充當兩個不同簽核層

### LVE-11｜假別週年制、曆年制與結轉（B）

**執行者**：HR。**起始條件**：企業需不同休假年度。

**操作**：
   1. 設定假別代碼、年度制、生效日期、是否結轉
   2. 核定個別員工額度
   3. 查看可用／待審／已核准

**預期**：時數依公司版本配置，歷史政策不可被無痕覆寫

**例外／權限驗證**：此為企業人事政策，不等於平台已自動認定全部臺灣法定假日

### LVE-12｜防止超額請假與重複扣除（B）

**執行者**：員工／HR。**起始條件**：可用額度 8 小時。

**操作**：
   1. 先送出 8 小時假期
   2. 送出另一筆重疊／超額 8 小時
   3. 主管核第一筆

**預期**：待審有保留帳，已核准只扣一次，超額必須有明確拒絕

**例外／權限驗證**：不能在重試或多層核准時重複扣同一額度

### LVE-13｜附件權限隔離（B）

**執行者**：員工甲／員工乙／主管。**起始條件**：甲已上傳私人病假佐證。

**操作**：
   1. 甲下載本人附件
   2. 主管下載所轄人員附件
   3. 乙嘗試以相同附件路徑下載

**預期**：甲與授權主管可下載；乙或跨企業用戶被拒絕

**例外／權限驗證**：不在網頁呈現永久公開 Storage URL

### LVE-14｜主管無法核准自己（A）

**執行者**：Owner／HR／主管。**起始條件**：某主管提出本人請假。

**操作**：
   1. 主管本人登入審核中心
   2. 檢查核准按鈕不可用
   3. 用本人 JWT 測試審核 RPC

**預期**：DB 層拒絕自我審核，不能靠 UI 隱藏

**例外／權限驗證**：Owner 也不可直接審核自己的申請

### LVE-15｜跨公司或平行部門越權審核（A）

**執行者**：他公司 Owner／平行部門主管。**起始條件**：A 部門員工請假。

**操作**：
   1. B 部門主管查審核
   2. 他公司 Owner 嘗試帶同一申請 UUID 呼叫審核 RPC

**預期**：不能讀取或核准非授權申請，原 pending 不變

**例外／權限驗證**：任何非法測試應用獨立 QA 帳號，不觸及真實員工

### LVE-16｜已核准請假取消／變更（A）

**執行者**：員工／HR。**起始條件**：已核准休假但行程更動。

**操作**：
   1. 員工申請撤銷或改日期
   2. 主管複核
   3. 額度及班表同步重算
   4. 查稽核差異

**預期**：取消與修改需有獨立歷程、不能任意覆寫核准紀錄

**例外／權限驗證**：2026-11-12 已有取消、改期與正式 Auth E2E 的實作及部分驗收；仍應依 E2E-12／13 在最新版本重驗多層簽核、月結、額度、重複核准與權限。不可把既有證據當本輪全數通過。

### LVE-17｜代理主管與法定假別版本（C）

**執行者**：HR／代理主管。**起始條件**：主管請長假、公司政策生效日變更。

**操作**：
   1. 指派代理主管及可審期限
   2. 員工送單
   3. 代理審核
   4. 切至新法規生效日重算

**預期**：每筆審核保留代理身分及規則版本，不能自行擴權

**例外／權限驗證**：目前法遵假別與審核代理流程未達正式完整驗收


## 06｜通知、LINE 登入與 OA

站內通知先可靠，LINE 實際發送須有 Channel 憑證與測試收件人。本節共 10 案。

### LINE-01｜員工讀取站內通知（A）

**執行者**：員工。**起始條件**：主管剛發布班表或審核請假。

**操作**：
   1. 開「通知收件匣」
   2. 查標題、產生時間與未讀
   3. 點「標記已讀」
   4. 刷新

**預期**：更新本人通知 read_at，不影響其他員工

**例外／權限驗證**：DEMO 可選虛構員工；正式模式不得切成他人收件人

### LINE-02｜沒有 LINE 也能使用網頁（A）

**執行者**：員工。**起始條件**：已登入企業帳號，但沒有 LINE 綁定。

**操作**：
   1. 直接從網頁查排班、打卡、假勤
   2. 在通知收件匣查結果

**預期**：核心人資操作不因未綁 LINE 完全失效

**例外／權限驗證**：不可把站內通知誤標為已送達 LINE

### LINE-03｜員工以 LIFF 綁定身分（B）

**執行者**：正式企業員工。**起始條件**：平台 LINE Login Channel／LIFF 已配置；本人有帳號。

**操作**：
   1. 開「LINE 通知」
   2. 查看配置狀態
   3. 點「以 LINE 驗證並綁定」
   4. 同意授權後返回

**預期**：伺服器驗證 LINE ID Token 並綁已認證員工 UUID

**例外／權限驗證**：目前缺乏實際成功綁定紀錄，須用真實 LINE 帳號和已配置的 LIFF 驗收

### LINE-04｜解除與重新綁定 LINE（B）

**執行者**：員工。**起始條件**：本人已綁定 LINE。

**操作**：
   1. LINE 通知→解除我的綁定
   2. 確認
   3. 使用正確 LINE 再綁一次
   4. 查是否只剩有效對應

**預期**：解除後停止對舊 LINE 身分送新通知；新身分需重驗證

**例外／權限驗證**：不能用其他員工 JWT 解除他人的身分對應

### LINE-05｜企業 HR 查看 LINE 發送狀態（B）

**執行者**：HR。**起始條件**：有待發送通知，員工已綁 LINE。

**操作**：
   1. 進 LINE 通知
   2. 按重新檢查
   3. 檢視 Channel 與 token 配置
   4. 對最多 5 筆執行發送

**預期**：API 接受／失敗數可回報；不宣稱接收者已讀

**例外／權限驗證**：Channel 未設好應顯示不可用；不可輸出 access token

### LINE-06｜平台 OA 實際推播（B）

**執行者**：平台授權管理者／員工。**起始條件**：官方 Channel token、LINE 接收人與 Messaging API 配額均可用。

**操作**：
   1. 觸發排班發布或核准
   2. 佇列中查通知
   3. 執行發送
   4. 用真實手機查 LINE 收件

**預期**：實收 Flex／文字內容與正確企業、員工及事件一致

**例外／權限驗證**：已部署 Edge Function 不代表已成功送達；目前無實際綁定／投遞紀錄

### LINE-07｜企業自有 LINE OA 模式（C）

**執行者**：企業 Owner。**起始條件**：企業自行有 LINE OA、Messaging API Channel。

**操作**：
   1. 完成 OAuth 或安全設定 Channel
   2. 驗證授權與簽章
   3. 將員工入口掛入自身 Rich Menu
   4. 發送一則測試訊息

**預期**：每家企業有獨立憑證、對象、配額和通知來源

**例外／權限驗證**：目前前端明示僅平台 OA 接通，店家自有 OA 尚未正式交付

### LINE-08｜LINE 對話指令及一鍵核准（C）

**執行者**：員工／主管。**起始條件**：已綁 LINE OA。

**操作**：
   1. 員工在 OA 點「我的班表」
   2. 點「我要請假」
   3. 在 LIFF 填表
   4. 主管收到待審訊息點查看與核准

**預期**：最終核准仍要登入身分和授權確認，不能靠自由文字直接更改 DB

**例外／權限驗證**：對話式入口及 Flex Message 一鍵流程尚未完成

### LINE-09｜訊息額度、去重與成本預警（C）

**執行者**：平台管理者／企業 Owner。**起始條件**：多家企業同時大量出現事件。

**操作**：
   1. 查看每企業發送數與配額
   2. 同一通知事件重送
   3. 達上限轉站內通知
   4. 查看本月成本

**預期**：不可重複計費或無上限發送；需可審計的送達狀態和配額

**例外／權限驗證**：目前尚未完成整套 SaaS 用量／費用營運頁

### LINE-10｜LINE 授權失敗或封鎖 OA（C）

**執行者**：員工。**起始條件**：LINE 未授權、封鎖 OA 或訊息 API 失敗。

**操作**：
   1. 嘗試發送
   2. 記錄平台回應碼與重試排程
   3. 顯示站內通知備援

**預期**：不影響正式人事資料；不可一直狂送消耗配額

**例外／權限驗證**：實際第三方失敗恢復流程尚需 Channel 真機驗收


## 07｜工時、月結、報表與薪資資料

7 日查詢、明細 CSV、月結快照、例外調整。本節共 10 案。

### RPT-01｜主管查看七日工時（A）

**執行者**：主管。**起始條件**：團隊已有上下班打卡資料。

**操作**：

   2. 指定查詢起始日期
   3. 點查詢
   4. 檢查員工時數、未完成事件

**預期**：以 IN／OUT 成對估計工時並標示缺卡；不等於正式薪資

**例外／權限驗證**：不同角色只能見有權人員

### RPT-02｜員工下載本人出勤明細（B）

**執行者**：員工。**起始條件**：有跨週、跨月打卡。

### RPT-03｜HR 依門市／部門／員工篩選（B）

   3. 查詢
   4. 匯出 CSV

**預期**：結果僅包含交集範圍且與畫面一致

**例外／權限驗證**：不得從資料限制不足的選單洩漏別家公司員工

### RPT-04｜匯出文字與 CSV 安全（A）

**執行者**：HR。**起始條件**：查詢結果含中文姓名及特殊符號測試值。

**操作**：
   1. 匯出 CSV
   2. 在試算表開啟
   3. 比對姓名、時間、工時
   4. 確認有 BOM、公式注入防護

**預期**：保留可讀中文且防止 =、+、-、@ 內容成為試算表公式

**例外／權限驗證**：不可把秘鑰、JWT、私人附件連結輸出

### RPT-05｜月工時行政試算（B）

**執行者**：HR。**起始條件**：該月排班、打卡、假勤資料完整。

**操作**：
   1. 開「月度工時與月結」
   2. 選月份
   3. 按「試算本月工時」
   4. 核對排定、觀察、假勤與不完整次數

**預期**：試算可重新產生，不等於已鎖定；成本僅預估

**例外／權限驗證**：法律認定工時、加班費、補休與工資尚需另行核對

### RPT-06｜月結前異常補正（B）

**執行者**：HR／主管。**起始條件**：報表顯示有未完成事件。

**操作**：
   1. 先到出勤異常掃描
   2. 指派員工提出補卡
   3. 主管審核
   4. HR 再試算

**預期**：月結前看見修正影響，留下更正而非直接改原始出勤

**例外／權限驗證**：不可單靠補卡申請存在就把未核准時間當實際出勤

### RPT-07｜月結鎖定（B）

**執行者**：Owner／HR。**起始條件**：已試算且確認月份無重大問題。

**操作**：
   1. 按「確認鎖定月結」
   2. 二次確認
   3. 刷新
   4. 再嘗試修改同月班次

**預期**：產生不可覆寫快照，已結月份不允許一般操作直接改動

**例外／權限驗證**：同一月份不可重複形成不同的正式快照

### RPT-08｜已結月份另開調整單（B）

**執行者**：Owner／HR。**起始條件**：某月已鎖定；員工補正 30 分鐘。

**操作**：
   1. 在月結頁按「新增調整單」
   2. 選員工、正負分鐘與原因
   3. 送出
   4. 匯出更正資料

**預期**：原快照不變，更正資訊以另一筆歷程保留

**例外／權限驗證**：不得由普通員工擅改已結月

### RPT-09｜預估人力成本（B）

**執行者**：Owner／HR。**起始條件**：具有時薪設定與可觀察工時。

**操作**：
   1. 查月工時試算及預估成本
   2. 與打卡原始明細對照
   3. 僅做行政參考

**預期**：只有授權 HR／Owner 可讀取敏感時薪；估算不直接發薪

**例外／權限驗證**：不應讓前端通用 wm_members REST 讀取任意時薪

### RPT-10｜正式薪資核發、勞檢與保存（C）

**執行者**：HR／企業負責人。**起始條件**：需要依法計算加班、休假工資與留存。

**操作**：
   1. 指定適用工時制度
   2. 計算法定加班／休息例外
   3. 覆核更正
   4. 匯出符合外部薪資格式與留存證據

**預期**：必須具備適用法規、版本、核准紀錄及可追溯證據

**例外／權限驗證**：完整薪資核發不在本產品既有非目標；工時法遵與匯出仍需正式驗收


## 08｜平台營運、資訊安全與正式上線

多租戶、權限、測試隔離、營運與外部依賴。本節共 10 案。

### OPS-01｜跨租戶讀取隔離（A）

**執行者**：不同公司 Owner。**起始條件**：A、B 兩家虛構企業。

**操作**：
   1. 用 A JWT 查看 A 資料
   2. 用相同 JWT 修改請求 tenant_id 為 B
   3. 再用 B JWT 比較

**預期**：A 身分無法讀寫 B 公司員工、班次或申請

**例外／權限驗證**：不能以隱藏前端選單當授權驗收

### OPS-02｜公開 DEMO 不可存取正式公司（A）

**執行者**：匿名測試者。**起始條件**：同時存在正式企業。

**操作**：
   1. 匿名使用 DEMO
   2. 嘗試指定正式 tenant ID 查詢／修改
   3. 檢查資料及錯誤

**預期**：匿名操作只對固定虛構 tenant 有效；正式公司資料無任何讀寫權

**例外／權限驗證**：DEMO 資料共用但不代表可觸碰其他真實企業

### OPS-03｜員工不得看到敏感時薪（A）

**執行者**：一般員工。**起始條件**：Owner 已為某員工設定時薪。

**操作**：
   1. 員工打開名冊／報表
   2. 用員工 JWT 直接請求 wm_members 敏感欄位
   3. 核對結果

**預期**：權限與資料庫欄位級 GRANT 阻擋不適當時薪查詢

**例外／權限驗證**：不可把時薪存在前端 HTML 隱藏欄位

### OPS-04｜手機 390px 組織與審核（A）

**執行者**：Owner／主管／員工。**起始條件**：Chromium 模擬 390px 窄螢幕。

**操作**：
   1. 開啟側邊選單
   2. 依角色進組織、申請、審核
   3. 打開表單
   4. 按返回

**預期**：不應橫向溢出或被選單蓋住；關鍵按鈕可點

**例外／權限驗證**：實機需另核對 iPhone／Android 鍵盤與 LIFF 視窗

### OPS-05｜兩個工作階段同步操作（B）

**執行者**：兩位主管／員工。**起始條件**：A 與 B 同時開同公司頁。

**操作**：
   1. 兩人幾乎同時審核同一申請或移動同一班次
   2. 重新整理
   3. 核對 DB

**預期**：僅第一個符合規則的提交成功；另一人收到更新／衝突訊息

**例外／權限驗證**：不能產生重複審核或重複工時

### OPS-06｜資料更新失敗與手動刷新（B）

**執行者**：所有使用者。**起始條件**：Supabase 暫時無法連線。

**操作**：
   1. 開網站
   2. 觀察連線狀態
   3. 網路恢復後點「更新」
   4. 核對已儲存資料

**預期**：網路失敗時提供明確重試，不得顯示假的操作成功

**例外／權限驗證**：避免每隔幾秒無理由全頁 reload 或無限輪詢

### OPS-07｜多企業方案、試用與席位計費（C）

**執行者**：平台管理者／Owner。**起始條件**：新企業希望選擇免費與付費方案。

**操作**：
   1. 選方案
   2. 查席位與分店額度
   3. 下單
   4. 由可信任支付回呼啟用權益
   5. 查看費用紀錄

**預期**：帳單與權益由可信任後端控制，不能由瀏覽器自設 paid

**例外／權限驗證**：尚未完成定價、付款業者授權、平台訂閱與方案配額

### OPS-08｜公司自有品牌／LOGO／政策管理（C）

**執行者**：Owner。**起始條件**：企業想套用品牌色、LOGO 與自訂規章。

**操作**：
   1. 上傳 LOGO
   2. 設定企業色與政策
   3. 在員工端查企業名稱
   4. 切換別家公司驗證隔離

**預期**：不同公司視覺與規範各自生效，不影響共享系統安全

**例外／權限驗證**：目前尚非完整品牌自訂管理平台

### OPS-09｜客服工單、備援與資料保留（C）

**執行者**：Owner／平台營運。**起始條件**：需要退出平台或資料保存期限屆至。

**操作**：
   1. 提交客服工單
   2. 查處理狀態
   3. 申請匯出與備份
   4. 依法保存或刪除

**預期**：所有存取留痕、依規則最小化資料與還原流程

**例外／權限驗證**：正式客服、長期備份、DR 演練與保存政策仍需驗收

### OPS-10｜上線前非功能驗收（C）

**執行者**：測試工程師／Owner。**起始條件**：使用隔離 QA 租戶和合法測試帳號。

**操作**：
   1. 執行大量員工／跨店資料測試
   2. RLS 越權檢查
   3. 手機及 LINE 真機
   4. 檢查日誌、效能與還原

**預期**：通過獨立負載、資安、法遵、可用性測試後才能稱正式可上線

**例外／權限驗證**：現有自動化斷言不能取代全站滲透測試及法遵核定

### E2E-01｜訪客從公開 DEMO 了解系統，再開立自己的公司

- **情境**：早餐店老闆想先試用排班，再正式導入。
- **角色與前置**：未登入訪客；另備全新測試 Email。
- **逐步操作**：
  1. 開啟 \`https://hub-google.github.io/LINE/workforce/\`，確認右上顯示「公開 DEMO」及測試資料提示。
  2. 依序點「總覽」→「排班管理」→「出勤打卡」→「差勤申請」→「工時報表」，確認畫面可載入，沒有強迫註冊。
  3. 按「企業登入」→「註冊」，填虛構信箱與密碼；依 Auth 設定進行信箱確認。
  4. 登入並選「建立企業」，輸入「星河服務 QA」，進入企業模式。
  5. 登出後重新登入，確認公司仍存在、DEMO 更動不等於正式公司資料。
- **預期／反向測試**：每次切換模式後租戶名稱一致；網路失敗時不能顯示虛構的「建立成功」；錯誤密碼不顯示任何正式資料。
- **證據**：DEMO 提示、登入狀態、建立企業成功畫面、登出再登入後的公司選單；測試結果 \`待執行\`。

### E2E-02｜邀請四類員工，建立三級主管鏈

- **情境**：公司開新店，Owner 要建立 HR、經理、組長與員工的管理順序。
- **角色與前置**：Owner 已登入星河公司；四個各自獨立的虛構 Auth 身分。
- **逐步操作**：
  1. 「員工與分店」建立台北店、板橋店與對應部門。
  2. Owner 新增／邀請 HR、王經理、林組長、張一凡、李小晴，設定人員角色、門市、聘僱型態。
  3. 受邀者在自己的裝置打開單次邀請連結，完成註冊／登入及接受邀請。
  4. Owner 設定 \`Owner → 王經理 → 林組長 → 張一凡\`，另將李小晴指派至林組長。
  5. 王、林、張分別登入「員工與分店」及「審核中心」，核對可見成員。
  6. 嘗試用已用過、過期或不符 Email 的邀請連結再加入。
- **預期／反向測試**：王能管其管理鏈、林只管理下屬、張無法提升自己的角色；邀請只能使用一次；不同公司的人員不能用同一邀請任意加入。
- **證據**：組織階層畫面、邀請狀態、各帳號可見範圍、RLS／角色變更拒絕紀錄；\`待執行\`。

### E2E-03｜兼職員工同時任職兩家企業

- **情境**：李小晴同時在星河服務與海角工作室兼職，但不應看見另一家的員工名冊。
- **前置**：兩個獨立正式租戶與同一個受邀者 Auth 身分。

  4. 在具備合法 LINE 憑證時綁定身分、執行一次授權的發送並到真實裝置查實收。
  5. 模擬封鎖 OA、取消綁定、重複事件、配額不足與發送失敗。
- **預期／反向測試**：站內通知有資料≠ LINE 已送達；真正送達需有接收裝置佐證；企業自有 OA、對話式核准等未交付功能應標 \`BLOCKED\`。
- **證據**：站內通知前後狀態、發送佇列、API 回傳、真機收件畫面或外部阻礙；\`待執行\`。

### E2E-18｜主管查週工時，HR 月結後用調整單追溯

- **情境**：HR 月底結算，發現張某天忘記打卡，補卡在月結後才核准。
- **角色與前置**：已排班、已打卡與一筆出勤異常；Owner/HR 有月結權限。
- **逐步操作**：
  1. 主管開「工時報表」，先看七日工時、出勤明細，依分店／部門／員工／日期篩選。
  2. 下載明細 CSV，確認當月與跨夜資料、休息扣除與未成對打卡呈現。
  3. HR 打開「月度工時與月結」，選目標月份、點「試算本月工時」。
  4. 確認試算內容後按「確認鎖定月結」，重新整理核對快照狀態。
  5. 模擬結算後合理更正，用「新增調整單」輸入分鐘差與原因，再匯出。
  6. 將同月份再次按月結或嘗試直接改舊原件。
- **預期／反向測試**：月結快照不被覆蓋；更正另行記錄；CSV 不得外洩非授權員工資料；試算金額不可宣稱等同依法可直接發薪。
- **證據**：明細 CSV、月結前後快照、調整單、權限拒絕；\`待執行\`。

### E2E-19｜出勤與補卡 5 年歷史 CSV，超大量也不能漏筆

- **情境**：離職員工依法請求歷史記錄，公司需匯出原始打卡、補卡、審核、更正資料。
- **角色與前置**：正式企業可授權人員；測試資料含跨年度與大量補卡簽核歷程。
- **逐步操作**：
  1. 開「工時報表」的歷史資料匯出介面，選指定員工、開始與結束日期。
  2. 先選正常短範圍匯出，檢查 UTF-8 BOM、中文欄名、Excel 開啟與每類記錄。
  3. 延伸至五年範圍；用大於 API 單批上限的虛構資料驗證逐頁下載。
  4. 比對伺服器準備匯出的 \`punch_count\`、\`correction_count\`、\`action_count\`、\`adjustment_count\` 與 CSV 實際列數。
  5. 用一般員工試圖匯出同事、跨部門人員或其他租戶的 ID。
  6. 測試無效時間區間、期間超限、分頁中途失敗、CSV 以 \`=+\-@\` 開頭的內容。
- **預期／反向測試**：任一類筆數不符應中止而不是產出「看似完整」檔案；原始打卡不與核准補正混為一列；只有伺服器授權的會員與期間可匯出。
- **證據**：匯出 CSV（僅虛構資料）、每類筆數核對、越權 403、錯誤情境；\`待執行\`。

### E2E-20｜手機、失敗重試、並行操作與未交付功能清單

- **情境**：員工在手機網路不穩時打卡，主管同時審核，Owner 用電腦查看。
- **角色與前置**：員工／組長／Owner；Chrome 手機窄版及桌面版，兩個獨立登入工作階段。
- **逐步操作**：
  1. 以 390px、430px 與桌面寬度逐頁走過「總覽、排班、打卡、差勤、審核、員工與分店、工時、系統資訊」及動態新增的通知／LINE／QR／異常／月結入口。
  2. 展開、關閉側邊選單與表單；確認主要操作按鈕不溢出、遮蓋、無法點擊。
  3. 模擬離線、API 401／403／429／5xx，確認畫面指出失敗、可安全重試，無假的成功提示。
  4. 同一假單兩位主管同時按核准，確認至多一次狀態變更；重載後資料一致。
  5. 測試過期登入、登出後返回上一頁、切企業瞬間切換資料、不同角色 URL/RPC 越權。
  6. 對尚未完成項目（完整 LINE Rich Menu／企業 OA／對話式指令、外勤離線補傳、合法薪資計算、訂閱付費與備份還原等）逐一標 \`BLOCKED / NOT IMPLEMENTED\`，不得補假按鈕或認定 PASS。
- **預期／反向測試**：重試不重複寫入、錯誤明確、權限由後端執行；跨裝置畫面可操作；不存在的功能不偽稱完成。
- **證據**：每頁手機／桌面截圖、狀態／RPC 時序、缺陷連結、未完成清單；\`待執行\`。
